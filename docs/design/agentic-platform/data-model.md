# Agentic Platform data model

> Status: proposed persistence contract.
> Baseline: `9b1c04e8927e195b8e8e23c7b1261756067ee25f` (2026-07-24).
> Depends on the shared decisions in [README.md](README.md).

This document defines the proposed Postgres ownership model for agent
identities, provider connections, durable execution, ChangeSets, approvals,
signals, and incidents. It is intentionally more explicit than an ORM sketch:
site deletion, credential erasure, retention, idempotency, and malformed-row
behavior are part of the contract.

## 1. Goals

- Every row that can reveal a tenant's content, policy, activity, or provider
  usage has a canonical `site_id`.
- Internal Runtime Agents and external MCP clients resolve to a persisted agent
  principal with exact scopes and revocation state.
- Provider credentials are referenced through a vault boundary and never
  appear in ordinary connection, run, action, audit, or API rows.
- Runs and actions are retry-safe and retain enough redacted evidence for
  operators to explain what happened.
- ChangeSet plans and approvals are hash-bound so a decision cannot authorize a
  different operation set.
- High-volume signals have explicit retention and deduplication rather than
  turning `np_audit_events` or job logs into an unbounded security lake.
- Site deletion covers the complete graph in a deterministic order.

## 2. Non-goals

- Storing raw provider chain-of-thought, unrestricted prompt transcripts,
  request bodies, cookies, authorization headers, or complete log streams.
- Replacing `np_audit_events`. Material agent mutations also create normal
  audit events; agent tables explain orchestration around those mutations.
- Making credentials, signals, incidents, approvals, or agent execution history
  portable through content export.
- Persisting source code changes from a Build Agent. Repository history and CI
  artifacts remain the build-plane record.
- Adding collection tables through the Runtime Agent. Collection definitions
  remain codegen and migration owned.

## 3. Shared row rules

Unless a table says otherwise:

- primary ids are UUIDs generated by Postgres;
- `site_id` is a non-empty canonical NexPress site id;
- timestamps use `timestamptz` and wire as canonical UTC ISO strings;
- state/kind columns are text with database checks matching the client-safe
  contract, avoiding an unchecked free-form state;
- JSON columns use exact bounded analyzers before write and after read;
- unknown state, malformed JSON, invalid scope, or cross-site reference fails
  closed and reaches Doctor/Health;
- API responses never rely on framework `Date` serialization;
- caller-provided idempotency keys are bounded, opaque strings and are compared
  only within their declared site/principal/capability scope;
- user deletion uses `SET NULL` for historical attribution; site deletion
  deletes site-owned history.

## 4. Identity and configuration tables

### 4.1 `np_agent_principals`

One revocable site-scoped identity for either an internal configured agent or
an external client.

| Column                  | Type                 | Rules                                                       |
| ----------------------- | -------------------- | ----------------------------------------------------------- |
| `id`                    | uuid PK              | Generated                                                   |
| `site_id`               | text                 | Required; indexed                                           |
| `kind`                  | text                 | `runtime` or `external`                                     |
| `name`                  | text                 | 1–120 display characters                                    |
| `description`           | text nullable        | Bounded operator text                                       |
| `status`                | text                 | `active`, `suspended`, or `revoked`                         |
| `scopes`                | text[]               | Sorted, unique exact `NpAgentScope` values                  |
| `authority_kind`        | text                 | `user` or `deployment`                                      |
| `authority_user_id`     | uuid nullable        | Required for live user authority; `SET NULL` after deletion |
| `authority_policy_id`   | text nullable        | Required only for deployment authority                      |
| `authority_fingerprint` | text                 | Immutable non-PII authority attribution                     |
| `authority_deleted_at`  | timestamptz nullable | Set when user authority is tombstoned                       |
| `token_version`         | integer              | Positive; initialized at 1 and monotonically incremented    |
| `owner_user_id`         | uuid nullable        | Staff owner; `SET NULL` on user deletion                    |
| `created_at`            | timestamptz          | Required                                                    |
| `updated_at`            | timestamptz          | Required                                                    |
| `revoked_at`            | timestamptz nullable | Required when status is `revoked`                           |

Constraints:

- `(site_id, id)` is the canonical tenant identity;
- `token_version` starts at `1`; zero/negative values fail DB/analyzer/Doctor;
- `revoked_at` is null unless status is `revoked`;
- one principal never changes `site_id` or `kind`;
- at creation and while active, exactly one authority reference matches
  `authority_kind`; deleting user authority first suspends the principal,
  revokes its credentials/grants, then nulls `authority_user_id` and sets
  `authority_deleted_at` while retaining the kind/fingerprint tombstone;
- an external principal's name, description, and scopes may change only
  through the audited Gateway Admin service; every scope-set change requires
  current `admin.manage` and increments `token_version`;
- every `active` principal's current scope projection contains `site:read`;
  removing it atomically suspends the principal and blocks new credentials,
  grants, tokens, and runs rather than leaving an unusable active identity;
- narrowing is effective immediately because every authorization intersects
  the credential/grant snapshot with the current principal scopes; widening
  never changes an existing OAuth grant, access-token, refresh family, or
  service-token scope snapshot, so newly added scopes require fresh consent
  and a new grant/token;
- `revoked` is terminal. Resuming a suspended external principal to `active`
  revalidates the same site, live authority, a current scope set containing
  `site:read`, and at least one still-live credential or grant. “Still-live”
  means an `active_head` service token or unexpired `overlap` token with
  matching family/principal authority versions and audience, or an `active`
  unexpired OAuth grant/refresh family with matching grant/principal versions;
  every expiry, overlap, status, site, resource, and authority check must pass
  at resume time. Resume never restores or widens revoked, consumed, expired,
  or overlap-expired material and never decrements `token_version`;
- a runtime principal's scopes are a projection of its active immutable Agent
  version and cannot be edited through the principal service. Runtime autonomy
  and capability modes remain version-owned and are resolved into run context,
  not copied onto the generic principal row. Widening or narrowing requires
  version activation; urgent containment pauses the Agent and may suspend the
  projection. It returns to `active` only as part of the Agent
  paused→active/version-activation transaction after exact version/status/
  scope validation, never through the Gateway principal resume route and
  never by inventing a credential/grant.

### 4.2 `np_agent_service_tokens`

Local automation and non-OAuth machine clients may use opaque service tokens.
Only their hashes are stored.

| Column                     | Type                 | Rules                                                                 |
| -------------------------- | -------------------- | --------------------------------------------------------------------- |
| `id`                       | uuid PK              | Generated                                                             |
| `site_id`                  | text                 | Must match the principal                                              |
| `principal_id`             | uuid                 | Required                                                              |
| `name`                     | text                 | Operator label                                                        |
| `prefix`                   | text                 | Exact derived `npst1_<lowercase-canonical-id>`; unique display id     |
| `token_hash`               | text                 | Unique versioned HMAC-SHA-256 verifier                                |
| `hash_key_id`              | text                 | Non-secret id in the dedicated token-hash keyring                     |
| `rotation_family_id`       | uuid                 | Stable family for replacement lineage                                 |
| `family_authority_version` | integer              | Positive immutable authority/scope/exposure generation for the family |
| `family_generation`        | integer              | Positive monotonic generation; unique per family                      |
| `replaces_token_id`        | uuid nullable unique | Prior same-site/principal/family token                                |
| `row_version`              | integer              | Positive optimistic-lock version                                      |
| `status`                   | text                 | `active_head`, `overlap`, `revoked`, or `expired`                     |
| `scopes`                   | text[]               | Sorted exact narrowing subset containing `site:read`; never implicit  |
| `transport`                | text                 | `stdio`, `mcp-http`, or `agent-http`                                  |
| `exposure_mode`            | text                 | Immutable `read`, `propose`, or `approved-execute` ceiling            |
| `audience`                 | text                 | Exact transport-bound audience                                        |
| `expires_at`               | timestamptz          | Required; bounded maximum lifetime                                    |
| `last_used_at`             | timestamptz nullable | Never used as authorization state                                     |
| `created_by`               | uuid nullable        | Staff creator                                                         |
| `created_at`               | timestamptz          | Required                                                              |
| `overlap_expires_at`       | timestamptz nullable | Old-token cutoff set when a replacement activates                     |
| `revoked_at`               | timestamptz nullable | Null while active                                                     |

The plaintext wire is exactly `npst1_<lowercase-canonical-id>_<secret>`.
Parsing the middle UUID selects the row; `prefix` is a checked generated
projection of `id`, never random or independently writable. The plaintext
token is returned once. Listing returns only id, name, prefix,
effective scopes, exposure mode, timestamps, and status. Remote MCP OAuth must
not be implemented by accepting one of these tokens as an upstream or
downstream provider token. The valid audience is
`urn:nexpress:agent-gateway:stdio` for `stdio`, the canonical
`https://<site-host>/api/mcp` resource for `mcp-http`, or the canonical
`https://<site-host>/api/agent/v1` resource for `agent-http`; a token is never
portable across those values.

One partial unique index permits only one `active_head` per
`(site_id, rotation_family_id)`. Rotation accepts only that head, locks it,
compare-and-swaps `row_version`, creates exactly one next family generation,
moves the old row to `overlap`, and makes the replacement `active_head` in the
same transaction. The unique predecessor prevents concurrent sibling
replacements. Rotate-versus-rotate and rotate-versus-revoke therefore have one
winner; the loser returns a version conflict and no plaintext token.

A pure credential rotation copies the same
`family_authority_version`, principal, scopes, transport, exposure mode, and
audience. Changing any authority field is not rotation: it revokes the old
family and creates a new family/authority version with fresh one-time material.

Rotation returns its replacement plaintext once,
and sets the old row's `overlap_expires_at` from the shared
`npAgentServiceTokenLimits`: default 15 minutes, hard maximum 60 minutes, and
never later than the old token expiry. Deployment policy may only shorten the
maximum; an overlap of zero revokes the old token as replacement activates.
Authorization accepts only `active_head` or a non-expired `overlap` row and
rejects at the earliest of credential expiry, overlap expiry, explicit
revocation, principal suspension/revocation, or authority loss; correctness
does not wait for cleanup. Either token can be revoked independently by id,
while principal/family revocation closes every remaining row. A bounded
retention reconciliation moves elapsed rows to `expired` and deletes only
metadata that is no longer needed for idempotency/audit.

### 4.3 OAuth client/grant storage

Remote interactive MCP uses the built-in NexPress OAuth 2.1 Authorization
Server rather than service-token passthrough or an external Agent Gateway token
issuer. An installed OIDC provider may authenticate the staff browser behind
consent, but NexPress owns the site grant, scopes, issuer, audience, token
rotation, revocation, and audit.

The built-in server adds:

- `np_agent_oauth_clients` — site-owned registered public-client id, exact
  redirect URI set, bounded metadata, registration source, and revocation
  state; v1 does not issue a client secret;
- `np_agent_oauth_requests` — one pending authorization/consent transaction
  with site, client, staff-session reference, exact redirect URI, bounded
  client `state`, requested scopes/resource and exact
  `nexpress_gateway_mode`, PKCE `S256` challenge, one-time
  consent-challenge verifier, status, and 10-minute expiry;
- `np_agent_oauth_grants` — client, staff resource owner, principal, site,
  approved scope subset containing `site:read`, approved immutable exposure
  ceiling, exact resource/audience, token
  version, positive consent generation, expiry, and revocation state;
- `np_agent_oauth_refresh_tokens` — grant/family id, current and parent token
  ids, versioned HMAC verifier plus hash-key id, status, expiry, consumed time,
  and replacement link so compare-and-swap rotation and replay-family
  revocation are durable;
- `np_agent_oauth_codes` — short-lived one-time authorization-code hash plus
  authorization-request id, grant, staff session, client, redirect URI, site,
  scope, exposure mode, resource, and PKCE `S256` challenge binding; the code hash also
  records its hash-key id.

The relational contract is:

- clients are unique by `(site_id, client_id)`, store a sorted exact redirect
  URI array, and have status `active` or `revoked`;
- requests have status `pending`, `authorized`, `denied`, `consumed`, or
  `expired`, store only the keyed consent-challenge verifier plus key id,
  status-consistent `authorized_at`/`denied_at`/`consumed_at`/`expired_at`,
  and are unique by that verifier;
- at most one `active` grant exists for one
  `(site_id, client_id, staff_user_id, resource, scope_hash, exposure_mode)`
  tuple; grant status is `active`, `revoked`, or `expired`, its positive
  consent generation is unique/monotonic for that tuple, and its authority
  version starts at `1` and increments monotonically;
- refresh rows have status `active`, `consumed`, `revoked`, or `expired`;
  `token_id` is a globally unique canonical lowercase UUID embedded as the
  `nprt1` public id, each verifier is unique, and exactly one active leaf may
  exist in a family;
- code rows have status `active`, `consumed`, `revoked`, or `expired`; their
  verifier is unique and exchange uses compare-and-swap from `active` to
  `consumed`;
- every row carries `site_id`, `created_at`, its applicable expiry/use/revoke
  timestamps, and same-site foreign keys. Status/timestamp contradictions fail
  closed and reach Doctor.

Authorization-code row id, authorization-request row id, and refresh
`token_id` are the bounded lookup ids in the exact `npac1`, `npoc1`, and
`nprt1` opaque verifier wires. Their persisted verifiers use the shared
purpose/site/id-bound `ov1` contract in
[security-and-credentials.md](security-and-credentials.md); no table accepts a
bare random token or a reusable hash from another material kind.

Access tokens are short-lived, audience-bound signed tokens and are not stored.
Their claims freeze the grant exposure ceiling alongside site, client, scope,
resource, grant, and authority versions. A later deployment/site widening does
not widen an existing grant or token; a broader profile requires fresh consent
or a new service-token family.
The dedicated Agent Gateway signing key and published verification-key adapter
are deployment secrets, not database rows and not the staff/member
`NP_SECRET`. Expired codes and refresh-token verifier rows are pruned in
bounded batches after their replay-detection window.

The authorize GET validates and persists exactly one `pending` request. Its
client `state` is bounded, treated as sensitive untrusted data, never logged or
used as authority, and echoed only to the already validated redirect URI.
Authorize POST consumes the consent challenge with compare-and-swap and moves
the request to `authorized` or `denied`; an authorized request creates the
grant/code in the same transaction. Replay, expiry, staff-session mismatch, or
any changed client/redirect/resource/scope/exposure/PKCE field fails closed.

The request state machine is exact:
`pending→authorized|denied|expired`, `authorized→consumed|expired`, and no
other transition. Successful token exchange locks the still-active code and
authorized request, rechecks every binding/expiry, and in the same transaction
moves both code and request to `consumed`, creates the refresh-family head,
and records the access-token mint claims/version. Invalid client, redirect,
PKCE, resource, or verifier attempts leave both rows unchanged; a replay sees
the terminal code/request and returns the same stable OAuth error without
minting. Expiry reconciliation moves due pending/authorized requests and their
still-active codes to `expired`. Denied/consumed requests are terminal.
Expired/revoked grants remain historical, never reactivate, and do not block a
fresh consent transaction from creating the next generation.

### 4.4 `np_agent_connections`

Metadata for one v1 model or notification connection. This row contains no
reusable secret.

```ts
export type NpAgentConnectionKind = "model" | "notification";

export type NpAgentConnectionSecretPurpose =
  "connection-credential" | "provider-oauth-pkce" | "provider-oauth-code";

export const npAgentProviderDataClasses = [
  "public-only",
  "internal-redacted",
  "sensitive-approved",
] as const;
export type NpAgentProviderDataClass = (typeof npAgentProviderDataClasses)[number];

export const npAgentProviderDataClassRank: Record<NpAgentProviderDataClass, number> = {
  "public-only": 0,
  "internal-redacted": 1,
  "sensitive-approved": 2,
};

export interface NpAgentModelPricingV1 {
  schemaVersion: "np.agent-model-pricing.v1";
  pricingId: string;
  version: number;
  fingerprint: string;
  modelId: string;
  currency: "USD";
  unitTokens: 1_000_000;
  inputMicrosPerUnit: number;
  cachedInputMicrosPerUnit: number;
  outputMicrosPerUnit: number;
  minimumRequestMicros: number;
  rounding: "ceil-each-component";
  effectiveFrom: string;
  effectiveUntil: string | null;
}
```

Pricing integers are non-negative safe integers,
`cachedInputMicrosPerUnit <= inputMicrosPerUnit`, and the effective interval is
canonical UTC with `effectiveUntil > effectiveFrom` when present. Exact
estimated cost is:

`fingerprint` is host-owned and is never accepted from an adapter. Define
`NpAgentModelPricingBodyV1 = Omit<NpAgentModelPricingV1, "fingerprint">`.
The rule fingerprint is
`pr1:sha256:<43-character-unpadded-base64url>` over SHA-256 of
`u32be(len("np-agent-model-pricing/v1")) ||
utf8("np-agent-model-pricing/v1") ||
u32be(len(rfc8785(body))) || rfc8785(body)`. The complete catalog is sorted by
`(modelId,effectiveFrom,pricingId,version)`, requires byte-unique complete
entries and non-overlapping intervals, and has fingerprint
`pc1:sha256:<43-character-unpadded-base64url>` over the same framed
construction with domain `np-agent-model-pricing-catalog/v1` and RFC 8785
bytes of the array including each verified `pr1` fingerprint. `pr1` and `pc1`
are closed raw digest kinds outside the 32-purpose canonical-JSON registry;
registration, config activation, provider admission, Doctor, and golden
vectors all use these exact builders.

```text
uncached = inputTokens - cachedInputTokens
max(minimumRequestMicros,
    ceil(uncached * inputMicrosPerUnit / 1_000_000) +
    ceil(cachedInputTokens * cachedInputMicrosPerUnit / 1_000_000) +
    ceil(outputTokens * outputMicrosPerUnit / 1_000_000))
```

All multiplication uses checked integer/BigInt arithmetic before a
safe-integer result. Admission reserves with requested maximum input/output
and `cachedInputTokens=0`; a negative/over-input cached count, overflow,
expired/missing price, another currency/rounding mode, or an adapter estimate
different from this formula fails closed. A provider-reported finalized cost
may differ and is retained in the reported bucket.

Pricing/model ids and catalog count use the shared
`npAgentProviderAdapterLimits` in
[security-and-credentials.md](security-and-credentials.md): each id is at most
128 characters and a snapshot has at most 256 entries. Unknown fields,
duplicates, or a catalog beyond those bounds fail before candidate
activation/persistence.

Security collectors, analytics, storage, workload identity, and
adapter-defined kinds need their own bounded consumer/result/idempotency
facets; they are future wire versions and are rejected in v1 rather than
represented by a ready connection that no executor can consume. Secret
purpose is closed to the three literal v1 values above—adapter-owned secret
purposes have no v1 lifecycle and fail parsing/Doctor.

V1 connection execution is credential-backed only: `api_key` and `oauth`
always resolve one active secret version/lease. Workload identity and
unauthenticated adapter calls require a future exact auth-context union and
call-attribution contract; they are rejected rather than represented as a null
credential.

| `updated_at`                       | timestamptz          | Required                                                   |

Changing provider, adapter contract, auth kind, or secret reference creates a
replacement connection or rotates the secret; it does not silently
reinterpret the old config. Editing non-secret config, model allowlist, or
data-processing ceiling uses the candidate-snapshot workflow below; a
credential-backed connection never exposes unprobed config as current.
Admitted runs/provider calls retain their frozen version/hash/classification.
Deleting/revoking a connection disables dependent agents before credential
erasure.

The credential/status matrix is exact:

| Status     | Active secret/version pair | Probe tuple                                               | Lease/admission |
| ---------- | -------------------------- | --------------------------------------------------------- | --------------- |
| `pending`  | both null                  | all four probe fields null                                | forbidden       |
| `ready`    | both non-null              | all non-null and both versions equal current              | allowed         |
| `disabled` | both non-null              | all non-null and both versions equal retained current     | forbidden       |
| `error`    | both null or both non-null | null with no pair; retained exact prior tuple with a pair | forbidden       |
| `revoked`  | both null                  | may retain its immutable historical tuple                 | forbidden       |

`active_secret_version_id`, `credential_version`,
`active_account_subject_key_id`, and
`active_account_subject_digest` are always all null or all non-null. A
non-null tuple resolves one same-site active
`connection-credential` secret-version row whose material/auth kind matches
`auth_kind`, whose positive version equals `credential_version`, and whose
account-subject digest is byte-equal. Notification connections additionally
require `active_destination_key_id`, `active_destination_descriptor`, and
`active_destination_fingerprint`, host-derived from the exact parsed active
descriptor plus that subject digest; all non-destination kinds keep all three
null.
The active connection and every admitted notification therefore retain every
member needed to rebuild `NpAgentConnectionDestinationCanonicalV1`; a
registry callback is used to verify, never invent, the historical descriptor.
`ready` is
the only leaseable state and additionally requires the current immutable
config snapshot, current config version, active credential version, and
non-null safe probe digest to be the exact successfully probed tuple;
`last_error_code` is null. `error` requires `last_error_code`; its retained
pair is only cleanup/reauthorization evidence and cannot be leased. Initial
setup/probe secrets remain pending secret-version rows referenced by the
operation, never by the connection's active pointer. Disable preserves the
last known-good pair for an explicit re-probe; revoke clears the pointer and
revokes/destroys the secret before completion. Database checks, service
analyzers, and Doctor enforce the same matrix.

#### Connection config versions

`np_agent_connection_config_versions` makes admitted adapter calls
reconstructable after an operator edits the connection:

| Column                        | Type                 | Rules                                           |
| ----------------------------- | -------------------- | ----------------------------------------------- |
| `id`                          | uuid PK              | Stable snapshot id                              |
| `site_id`                     | text                 | Required                                        |
| `connection_id`               | uuid                 | Same-site parent                                |
| `version`                     | integer              | Positive monotonic per connection               |
| `adapter_id`                  | text                 | Installed adapter id                            |
| `adapter_contract_version`    | integer              | Positive frozen adapter contract version        |
| `adapter_fingerprint`         | text                 | Frozen behavior/config-schema/auth digest       |
| `config`                      | jsonb                | Exact parsed non-secret adapter config          |
| `config_hash`                 | text                 | Canonical config/adapter digest                 |
| `pricing_catalog`             | jsonb                | Exact sorted `NpAgentModelPricingV1[]`          |
| `pricing_catalog_fingerprint` | text                 | Canonical catalog digest                        |
| `data_processing_ceiling`     | text                 | Frozen exact `NpAgentProviderDataClass`         |
| `state`                       | text                 | `candidate`, `active`, `retired`, or `rejected` |
| `created_at`                  | timestamptz          | Required                                        |
| `activated_at`                | timestamptz nullable | Required for active/retired                     |
| `retired_at`                  | timestamptz nullable | Set after a newer snapshot becomes active       |
| `rejected_at`                 | timestamptz nullable | Required only for rejected candidate            |

`(site_id, connection_id, version)` and `(site_id, id)` are unique. Rows are
immutable after creation except the exact `candidate→active|rejected` and
`active→retired` state/timestamp transitions. There is exactly one active
snapshot per non-revoked connection and at most one candidate attached to a
non-terminal config operation. The connection's current `config`, version,
hash, pricing catalog/fingerprint, data-processing ceiling, provider, contract
version, and `active_config_snapshot_id` are a checked byte-equal projection
of the active row and update in one compare-and-swap transaction. A retained
old snapshot therefore rehydrates its complete
`NpAgentConnectionConfigCanonicalV1` body without reading the connection's
newer ceiling.
A catalog is sorted by `(modelId, effectiveFrom, pricingId, version)`;
pricing-id/version/fingerprint tuples are unique, intervals for one model do
not overlap, and every allowlisted model has exactly one price effective at
candidate activation time. Editing any price creates and probes a candidate
config snapshot. Retired snapshots and their catalogs remain immutable while
referenced by a run, call, reservation, notification, audit, or retention
window; Doctor blocks pruning or execution when a referenced catalog digest
cannot be reproduced.
A snapshot remains while any Agent version, provider-OAuth setup request, run,
provider call, connection operation, or notification references it.
Adapter invocation constructs `NpAgentConnectionConfigSnapshotV1` only from
this row plus the byte-equal active connection/secret account-subject and
destination projection frozen at admission; no call reparses a newer config or
credential under an older hash.

`PATCH /api/admin/agents/connections/{id}` cannot change provider, adapter,
auth kind, or secret. With no active credential (`pending` or credentialless
`error`), it validates a full replacement config, revokes any open OAuth setup
request, activates the new snapshot/retire-old in one CAS, and leaves the
connection `pending` with its error cleared. With a retained active credential
(`ready`, `disabled`, or credentialed `error`), it creates a `candidate`
snapshot plus one Admin-authorized `activate-config` operation while the old
active snapshot/status remains authoritative. The worker leases the current
credential, probes the candidate bytes, and on success atomically
retires/activates snapshots, updates the connection projection and exact probe
tuple, then returns `ready` (or preserves `disabled`). Failure rejects the
candidate and leaves the old projection/status byte-for-byte unchanged; the
operation carries the safe error. No admitted call observes the candidate.

The callback resolves the row from the `npps1` public id and compares the keyed
hash in constant time. For a success callback, one database transaction locks
the row/connection and atomically: rechecks every frozen precondition; CASes
`pending→consumed`; creates the pending `provider-oauth-code` secret-version
metadata and linked `seal` vault-operation journal; and creates one
`oauth-exchange` connection operation in `awaiting_secret`, linked to the
auth request, code secret/vault operation, and existing PKCE secret. Only after
commit does the callback dispatch seal with its live code buffer. A sealed or
recovered vault receipt activates the temporary secret and CASes the linked
connection operation `awaiting_secret→queued` before enqueue. Seal input loss
terminally fails that connection operation with `VAULT_SEAL_INPUT_LOST`,
destroys the PKCE metadata/material, and requires a new authorization; no
consumed code/state is replayed.

For a provider denial, one transaction CASes `pending→denied`, sets
`denied_at` and exact `last_error_code:"AUTHORIZATION_DENIED"`, and journals
PKCE destruction. It creates no code secret, code vault operation, or
connection operation. A denial/success replay is terminal and returns the
same safe local outcome without another exchange or adapter call.

The adapter/provider/client, site, staff session, redirect URI, and PKCE
verifier plus frozen adapter/client/config fingerprints must all match current
installed deployment facts. A change requires a new setup request; it never
exchanges under new client semantics. Provider access/refresh tokens are
sealed as a new connection credential version; the temporary code/verifier
are destroyed after success and on failure/expiry cleanup. The authorization
code, raw state, verifier, provider token response, and provider error body are
never persisted in ordinary rows or logs.

OAuth start is one serialized candidate-credential workflow. `initial` is
allowed only for `pending` or credentialless `error` and freezes a null old
credential tuple. `replace` is allowed for `ready`, `disabled`, or
credentialed `error` and freezes the complete current secret/version/account
subject tuple; the old credential/status remains authoritative while consent
is outstanding (`disabled`/`error` remains unleaseable). At most one pending
request exists per connection. Start never clears or retargets the old pair.

After callback, the worker seals/probes a pending candidate. Replacement must
produce the same account-subject digest under the frozen key id; a different
provider account requires a new connection. Activation locks the connection
and compare-and-swaps expected status, active config snapshot/hash, secret id,
credential version, and account tuple. Initial success becomes `ready`;
replacement preserves `disabled` or returns `ready` from ready/credentialed
error, retires the old credential, then destroys it after leases drain. A
stale callback/CAS, failed probe, denial, or expiry leaves the old projection
byte-for-byte unchanged, destroys candidate/code/PKCE material, and records a
safe terminal result. Credentialless initial failure remains pending/error.

`awaiting_secret` is permitted only for `source:"oauth-setup"` plus
`kind:"oauth-exchange"` and requires the exact linked auth request/code
secret/vault operation. It has no worker lease/start time and cannot be
enqueued. Only the vault-operation reconciler may move it to `queued`, in the
same transaction that adopts a successful seal receipt; that transition sets
`deadline_at = min(now + 60 seconds, authRequest.expires_at,
codeSecret.expires_at)`, and refuses an already elapsed bound. A terminal seal
failure moves it to `failed`. All other operation kinds start `queued` with a
non-null deadline at admission, and no deadline is ever extended.

Admin test/rotate/enable commits one operation and enqueues
`agent:connectionOperate {siteId, operationId}` after commit, then polls this
row. Provider OAuth callback performs the atomic consumed/code-seal-journal/
`awaiting_secret` admission above and redirects the browser to a local pending
status page. After the reconciler proves the code sealed and queues it, the
worker leases code and PKCE once, rechecks all frozen
adapter/client/config fingerprints, exchanges, seals the returned credential
as a new pending connection-credential version, probes/activates it, and
destroys code/PKCE secrets on every terminal path.

OAuth code exchange is not blindly retried after an ambiguous provider
outcome. A crash/timeout after possible provider acceptance moves the
operation/connection to `ambiguous`/`error`, destroys temporary secrets when
safe, and requires fresh authorization. This avoids replaying a single-use
code under guessed semantics. Duplicate jobs reclaim only a still-safe
persisted phase.

`np_agent_invocations` reserves every Admin operation before this row is
created. Same authorization context/operation/idempotency key and request hash
returns the linked operation; a different hash conflicts. The provider OAuth
callback instead uses the compare-and-swap consumed
`np_agent_connection_auth_requests.id` as its sole operation authority and
server key `oauth-exchange:<authRequestId>`; a unique auth-request reference
creates at most one operation and never needs a caller-chosen callback key. A
runtime refresh has no new principal invocation: it is bound to one same-site
admitted run and uses the server key
`refresh:<connectionId>:<secretVersionId>:<refreshGeneration>`. A partial
unique index on that tuple coalesces concurrent runs; exactly one operation
may refresh an active generation. The three source branches and their
authority fields are exact: Admin requires only `invocation_id`, OAuth setup
only `auth_request_id`, and Runtime refresh only `run_id`; all other authority
ids are null.

When access material is expired or within the adapter-declared refresh skew, a
run creates/reuses that refresh operation and waits without opening a provider
call. The worker leases the expected credential once, invokes the exact
connection-auth adapter, seals the returned material as a new pending version,
probes it, then compare-and-swaps connection active-secret/version and refresh
generation. A CAS loser destroys its unreferenced new secret. Success retains
the same provider-subject digest, accepts only the requested permission set or
a narrower still-sufficient set, activates the new row, and retires the old.
`invalid-grant`, subject/permission mismatch, timeout/crash after dispatch, or
unknown provider acceptance moves the operation/connection to
`ambiguous`/`error`, never replays refresh, and requires fresh authorization.

`(site_id, connection_id, purpose, version)` is unique. At most one
`connection-credential` row per connection is `active`; short-lived PKCE rows
never become the connection's active credential. `secret_ref` and
`vault_adapter` are server-only and absent from Admin, API, MCP, OpenAPI,

destruction for attribution while their locator is cleared.

`aad_body`, `aad_digest`, and `vault_algorithm` are required for every secret
purpose and are the shared reconstruction authority even when an external
vault has no local entry. The body must repeat the row's exact site,
connection, purpose, secret id/version, adapter triple, envelope version, and
algorithm. It reparses and reproduces `aad_digest` before any seal/open/
inspect/rewrap/destroy operation. For `local-envelope`, the entry's algorithm
and AAD digest must be byte-equal; an external adapter receives the same body
bytes/digest and cannot substitute its own projection.

`seal_operation_id` and `np_agent_vault_operations.secret_version_id` are
same-site `DEFERRABLE INITIALLY DEFERRED ON DELETE NO ACTION` foreign keys.
PostgreSQL's `RESTRICT` action fires immediately even on a deferrable
constraint, so `NO ACTION` is required to preserve restrict-by-default
semantics while allowing the complete lifecycle component to be removed in
one verified transaction.
They deliberately form one lifecycle component: after destruction and both
retention deadlines, cleanup locks a destroyed secret plus every terminal
seal/rewrap/destroy operation that references it and deletes the complete
component in one serialized transaction. It never clears either reference or
prunes one side first. Any non-terminal/too-young/external dependent aborts
the whole prune; crash before commit leaves both sides and crash after commit
leaves neither.

The operation row and pending secret metadata commit before adapter dispatch.
Same adapter/key/digest reuses the row/receipt; a different digest conflicts.

acceptance compare-and-swaps both, so a lease-late result cannot advance a
newer transition. Retry uses the exact
`5,15,30,60,300,900,3600`-second capped ladder from the shared vault limits.
Timeout/crash moves to `waiting_inspection`, and `agent:eventReconcile`
enqueues `agent:vaultOperate {siteId, vaultOperationId}` even when no parent
connection operation exists. The exact frozen adapter must report `absent`
before rewrap/destroy redispatch. Seal may redispatch an absent result only
while its original process lease still owns the live single-use plaintext;
after process/lease loss it terminalizes as `VAULT_SEAL_INPUT_LOST` and
requires API-key re-entry or fresh OAuth authorization. Seal success
CAS-stores the recovered ref and links `seal_operation_id`; rewrap updates
ref/key metadata only from its receipt; destroy clears the ref only after
`destroyed|already_absent`.
Operation/secret rows retain the exact adapter implementation until every
lease, rewrap, inspection, and deletion completes. An orphan, mismatched
triple, uninspectable operation, or successful receipt without a linked secret
row blocks readiness/Doctor/site deletion.

Every `connection-credential` row requires the
`account_subject_key_id`/`account_subject_digest` pair, including API-key
material; temporary code/PKCE rows keep both null. OAuth connection
credentials additionally require access expiry, `refresh_token_present`,
positive refresh generation, and permission digest; refresh expiry is null
when no refresh token exists and may also be null when a refresh-bearing
provider omits expiry. Non-OAuth material forbids the five OAuth-only metadata
fields. Initial exchange cannot use
refresh mode `retain`. A refreshed version has
`refresh_generation=old+1`: `replace` seals new refresh bytes/expiry, `retain`
re-seals the leased old refresh bytes and preserves old expiry, and `none`
stores no refresh token/expiry. All branches zeroize buffers and cannot change
subject or silently widen permissions. A credential with
`refresh_token_present=false` cannot admit `oauth-refresh`; access expiry
requires fresh provider authorization.

Purpose, material kind, and decoded envelope are exact: a
`connection-credential` permits only `api_key|oauth` matching connection
`auth_kind`; `provider-oauth-pkce` permits only `provider_oauth_pkce`; and
`provider-oauth-code` permits only `provider_oauth_code`. All use
`credential_envelope_version=1`, but a provider credential lease rejects both
temporary branches.

The total graph is purpose-specific. Connection credentials follow
`pending→active|revoked|destroyed`, `active→retiring|revoked`,
`retiring→destroyed|revoked`, and `revoked→destroyed`. A temporary
`provider-oauth-pkce` or `provider-oauth-code` row follows only
`pending→destroyed` and never has activation/retirement timestamps. Destroy
requires the adapter's confirmed
`destroyed`/`already_absent` result and clears the locator; a revoked row
remains unusable while physical destruction is retried.

| `activated_at`                | timestamptz nullable | Required for active/retired                                        |
| `retired_at`                  | timestamptz nullable | Required for retired                                               |

`(site_id, agent_id, version)` is unique; at most one version is active and at
most one is draft. Active/retired versions are immutable. Activation validates
the complete effective contract, retires the old version, updates
`active_version_id`, synchronizes only the runtime principal's exact scope/
active-version relationship, and reconciles version-owned triggers in one
serialized transaction. Autonomy and capability modes remain version-owned
and are frozen into each admitted run. Pausing
changes lifecycle only, not the immutable version. An agent may run
deterministic recipes without a model connection. Archiving disables triggers
and preserves attributable versions/history.
`recipe_registry_body` uses
`np.agent-recipe-registry.v1`/`projection:"registry"`, contains the complete
non-empty installed set used at activation, and must reproduce
`recipe_registry_fingerprint`. Every configured recipe resolves to exactly one
definition in that retained body. The version remains dependency-retained
while any run/provider call/approval/audit fact needs a definition
fingerprint, so a deployment upgrade never recreates historical recipe bytes
from the new registry.

Agent and runtime-principal projection is one exact serialized state machine:

| Agent status | `active_version_id` | Runtime principal status/scopes                                     |
| ------------ | ------------------- | ------------------------------------------------------------------- |
| `draft`      | null                | `suspended`; empty scope projection                                 |
| `active`     | required            | `active`; exact active-version scopes including `site:read`         |
| `paused`     | required            | `suspended`; retain exact active-version scopes                     |
| `error`      | required            | `suspended`; retain exact active-version scopes                     |
| `archived`   | nullable history    | terminal `revoked`; retain last projection or empty if never active |

A failed draft/activation validation leaves the Agent `draft` or
`paused`—it does not invent an `error` Agent without an active version.
Activation/resume, pause/error containment, version replacement, and archive
lock both rows, update Agent status/version and principal status/scopes in one
transaction, and increment the principal `token_version` whenever projection
status, scopes, or active version changes. Archive sets `revoked_at`; neither
Agent nor principal can resume. Generic Gateway principal mutation/resume
routes reject `kind=runtime`; only these Agent transitions may change the
projection. Doctor blocks admission on any mismatched pair.

Activation resolves every settings branch against the exact recipe id/version,
template compatibility, provider mode, settings schema, trigger kinds, and
capability ceiling in the installed recipe registry. The Agent version's
config hash includes canonical settings plus every selected recipe
fingerprint/instruction/schema digest; a stale or unavailable definition
blocks activation rather than falling back to prose.

Every configured capability mode must be no more permissive than the version's
`autonomy`; absent capabilities are denied. The duplicated principal
projection exists for constant authorization lookup and must match the active
version or Doctor blocks admission. Every active Agent version and synchronized
runtime principal scope projection contains `site:read`; a draft without it
cannot activate.

Capability-mode entries are sorted/unique and absent ids are denied. The four
modes are permission sets, not an ordinal escalation ladder:

| Mode       | Read/observe | Create proposal/plan | Unattended reversible execution | Request/consume human approval |
| ---------- | ------------ | -------------------- | ------------------------------- | ------------------------------ |
| `observe`  | yes          | no                   | no                              | no                             |
| `advise`   | yes          | yes                  | no                              | no                             |
| `guarded`  | yes          | yes                  | yes, only when hard rules allow | no                             |
| `approved` | yes          | yes                  | no                              | yes                            |

Site, Agent-version, and every active policy layer compose by intersection.
The exact commutative meet is:

| meet       | `observe` | `advise`  | `guarded` | `approved` |
| ---------- | --------- | --------- | --------- | ---------- |
| `observe`  | `observe` | `observe` | `observe` | `observe`  |
| `advise`   | `observe` | `advise`  | `advise`  | `advise`   |
| `guarded`  | `observe` | `advise`  | `guarded` | `advise`   |
| `approved` | `observe` | `advise`  | `advise`  | `approved` |

Thus a human-only layer combined with a guarded layer becomes advisory, never
unattended. `approved` executes only after a valid human approval.
`guarded` executes only a capability/effect that is explicitly reversible or
expiring and whose hard/policy rules allow the exact target. After the meet,
the capability descriptor and server hard floor may only remove permissions
or raise the result to `approval_required`; they never convert `approved` to
unattended execution. An incompatible configured mode fails activation rather
than being guessed.

Budget numbers are safe non-negative integers; token/count fields are bounded
by signed 32-bit maximum, cost micros by JavaScript safe-integer maximum,
cooldown by 86,400 seconds, and `warningBasisPoints` by `0..10_000` (default
`8_000`). `null` means inherit the next outer ceiling, never unlimited. The
deployment budget is concrete with no nulls; site and Agent budgets may only
narrow it. `0` disables that dimension. Per-hour counters are rolling 60
minutes, per-day counters are UTC calendar days, and per-month counters are
UTC calendar months. Cost currency is USD in v1. A provider
adapter/connection without a validated exact USD-micros pricing contract is
unusable for provider-backed runs and fails admission regardless of which
narrower budget fields are set; v1 performs no undeclared exchange conversion
or token/call-only exception.

AP-101 implements this exact `NpAgentBudgetV1` in the client-safe contract.
The default analyzer permits `null` for site/Agent inheritance, while its
`requireConcrete` option rejects every `null` for the deployment projection;
both paths share the published count, cost, cooldown, and warning bounds.
Persistence, layer composition, counters, reservations, and Admin mutation
remain AP-102 and later work rather than being inferred by this wire parser.

`NpAgentRunLimitsV1` is the concrete non-null minimum resolved at admission
from deployment/site/Agent budgets and recipe hard bounds. Counts/tokens/cost
use the same integer maxima; attempts/calls are at least 1 for an admitted
run, and wall clock is `1..86_400` seconds. Its canonical hash and the
effective budget-source/counter/reservation snapshot are frozen on the run;
policy or budget edits cannot widen it after admission.

All policy arrays are sorted, unique, bounded to 100 entries (quiet-hour
windows to 8 and escalation channels to 5), and `null` means no additional
resource narrowing at that layer. Composition intersects non-null resource/
channel lists, takes the stricter capability/risk/severity threshold, the
higher automatic-confidence threshold, and the lower count/TTL/retention
ceiling. Provider data classification takes the numeric minimum of the
connection-owned ceiling and every active policy's
`npAgentProviderDataClassRank`; only an explicit `sensitive-approved` at every
layer can resolve that class. Severity uses the shared
`npAgentIncidentSeverityRank` (`info < low < medium < high < critical`):
minimum notification severity takes `max`; Guardian actor-limit severity is
disabled when any layer is null, otherwise it takes `max`. Quiet-hour windows
are non-overlapping UTC minutes in `0..1_440` and
compose by union as deny periods. Guardian TTL must stay within the frozen
60–3,600 second actor-restriction bounds; every day value stays within the
retention maxima in this document. Rules can narrow but never remove a
descriptor's human-approval floor.

a Gateway/manual run references its unique invocation rather than defining a
second capability-blind tuple. Unique
`(site_id, origin, principal_id, admission_fingerprint)` prevents duplicate
event/schedule/invocation admission. Worker reclaim/job retry increments
`attempt` on the same run and resumes its persisted steps; every claim and

provider-call row. Only the explicit `agent.run.retry` ops action creates a
newly admitted child run with `parent_run_id`, new invocation/admission
fingerprint, and newly resolved limits that can be no wider than the failed
run. None of these may duplicate a committed action.

has `root_run_id=id`, null parent, depth zero, and null causal action. A child
references an already-persisted same-site parent, copies its root, and has
exactly `parent.causal_depth + 1`; root/parent cannot be self-swapped,
cross-site, missing, or a descendant. A run admitted from a
causation-bearing event must copy that event's source run/action/root and set
`causal_depth=event.causation.depth+1`; an ordinary event/manual/Gateway root
cannot claim those fields. `NP_AGENT_CAUSAL_DEPTH_MAX` is 4. Depth overflow
creates no run/provider reservation, marks that trigger dispatch skipped with
`AGENT_CAUSAL_DEPTH_EXCEEDED`, and emits one deduplicated loop signal while
normal deterministic event handling continues. The admission fingerprint
includes root, parent, depth, causal event/action, trigger, and version so
switching Agent definitions cannot reset lineage.

immutable run deadline. Its approval expiry is

decision, and `execute_approved` invocation locks/rechecks the run and rejects
`now >= deadline_at`. A bounded reconciliation transaction at the deadline
moves the still-waiting run and action to `failed` with
`APPROVAL_DEADLINE_EXPIRED` and expires any pending/approved unconsumed
approval. Approve versus deadline and execute versus deadline serialize on
the same rows; a late approval cannot revive the run or be reused by a new
run. The caller must create a fresh proposal/action under a newly admitted
run.

The model never chooses `risk`, required scopes, or approval mode. Those come
from the registered capability plus active policy. `input_canonical`,
`required_scopes`, `target_refs`, `target_version_facts`, and the immutable
attribution/registry columns are the authoritative rehydration source for
`NpAgentActionCanonicalV1`; reparsing and rehashing them must reproduce
`input_hash`. Target facts have exactly the same refs/order as `target_refs`
and freeze each resource owner's current canonical version digest before
approval. Capability schemas may not accept reusable credentials or other
write-only secret material—those use the connection/vault Admin flow.
`capability_definition_body` uses
`np.agent-capability-registry.v1`/`projection:"definition"` with exactly one
capability; it must reproduce `capability_fingerprint` and the selected effect
profile/version before policy, approval, execution, verification, or
compensation.
`input_canonical` is server-only, encrypted at rest by the deployment storage
layer, excluded from logs/Admin/MCP projections, and retained for the entire
dependency-closed lifetime of the action row, its `input_hash`, and every
approval/execution/evidence reference that claims that proposal. Cleanup
deletes the canonical input, action/digest owner, and last such references in
one serialized transaction; it never clears `input_canonical` while retaining
`input_hash`. `input_redacted` is the separate safe UI/audit projection and is
never substituted into the hash.
`np_agent_invocations` is the cross-transport idempotency authority; this row
records the capability-step key and sequence without inventing a second,
principal-blind uniqueness boundary. An approval-required proposal keeps the
first invocation in `approval_required`; the exact `execute_approved`
invocation is stored separately in `execution_invocation_id` and may only
advance that same action after every frozen approval binding is rechecked.
Approval/reconciliation atomically maps reject, revoke, or expiry to action
`failed` with `APPROVAL_REJECTED`, `APPROVAL_REVOKED`, or
`APPROVAL_EXPIRED`. A linked run still in `waiting_approval` becomes `failed`
with the same code. A new attempt creates a new action/approval/invocation;
terminal rows never resume.

For a mutating action, effect profile/version, verifier id, receipt digests,
parsed output/hash, and optional derived undo reference are persisted in the
same transaction as the domain mutation wherever the domain store is
transactional. The action then remains `executing` with
`verification_state=pending` until the named verifier records
passed/failed/ambiguous result/evidence. A worker crash reclaims that exact
action/receipt; it never asks a model to reconstruct the effect. External or
post-commit ambiguity remains explicit. Only `passed` may move a normal
mutation to `succeeded`; failed/ambiguous follows the declared compensation or
manual-recovery path. A `completed-no-effect` execution has no receipt,
effect, undo, or verification fields and must prove its domain transaction
wrote nothing.

`succeeded -> compensated` is the only post-success state transition. It
requires the frozen compensator/undo ref, a target-version compare-and-swap,
and an exact compensation receipt; it may be initiated by an approved restore,
verification recovery, or declared containment expiry. It never reopens
provider reasoning, changes the original invocation result, or admits a new
capability under expired authority.

cannot authorize an action. Provider output must pass the exact decision
parser before `decision` is stored or another runtime step may consume it.

canonical provider request bytes; a mismatch fails before opening a credential
lease or reserving provider spend.
`request_redacted`/`response_redacted` are optional support projections and
never the digest body. Provider request/response are the two closed
hash-only-retention exceptions: independent codecs verify the exact
classified request or normalized outcome before the full diagnostic body is
discarded, while the row retains its digest and safe frozen facts. A later
Doctor check may verify those retained bindings but must not pretend the
redacted projection can reproduce the full digest.

request digest. The host recomputes all adapter-estimated USD-micros with that
rule; an adapter-provided estimate that differs is a malformed result.

sources, cost/currency, and finish reason. `succeeded` requires all three
token counters, `usage_source`, cost/currency/`cost_source`, latency, response
digest, parsed decision, and `finish_reason` in `stop|length|tool`.

complete known usage. A pre-dispatch failure/cancellation has all usage and
finish fields null; a normalized post-dispatch failure/cancellation stores
complete counters/sources/cost plus its exact finish reason. `ambiguous` has
null counters/cost/finish and both sources `unknown`. Known token counters are
all non-null together; known cost requires `"USD"` and source
`provider|adapter-estimate`; `unknown` requires null values. A row cannot
claim `provider` merely because an adapter estimated it.

`dispatch_state` is persisted in the same compare-and-swap as the normalized
outcome and included in `response_digest` and reservation reconciliation.
`reserved` starts `not-dispatched`; the pre-invoke commit moves it to
`in_flight/unknown`, so a worker crash cannot be mistaken for no dispatch.
`succeeded` is `dispatched`; `ambiguous` is `unknown`; a failed/cancelled row
uses the exact returned `not-dispatched|dispatched` branch. A
`not-dispatched` failure has null provider request id, usage, cost, and finish.
No retry or crash recovery infers dispatch from timestamps, provider id,
exception class, or missing usage.

### 5.5 Provider usage reservations and aggregates

Provider admission cannot be implemented by reading mutable JSON counters from
a run. It uses two site-owned tables under the same site advisory lock as run
admission:

`np_agent_usage_reservations` contains:

- `id`, `site_id`, `agent_id`, `run_id`, `connection_id`, and a
  caller-stable `idempotency_key`, unique as
  `(site_id, run_id, connection_id, idempotency_key)`;
- immutable `connection_config_snapshot_id`, concrete `model`,
  `pricing_id`, positive `pricing_version`, `pricing_fingerprint`, and
  `pricing_effective_at`, byte-equal to the parent run/call;
- state `reserved`, `reconciled`, `released`, or `expired`;
- maximum reserved calls, input/output tokens, and cost micros;
- nullable actual input/cached-input/output token and USD-micros counters;
- exact `actual_usage_source`/`actual_cost_source`, each null while untouched,
  `provider|adapter-estimate` with known values, or `unknown` with null actual
  values; an explicit `unpriced` flag is true only for that unknown branch;
- `budget_charge_cost_micros`, equal to known actual cost on reconciliation or
  the admitted maximum reservation when an ambiguity window expires unknown;
- `reserved_at`, `expires_at`, and nullable `finalized_at`.

`np_agent_usage_daily` contains one row per
`(site_id, agent_id, connection_id, usage_date)` with integer provider calls,
provider-reported and adapter-estimated token buckets, reported and estimated
cost micros, conservative budget-charge micros, and unknown/unpriced-call
count. These buckets derive only from finalized reservation source fields,
never response bodies or a mutable run aggregate. Reconciliation updates the
reservation and daily aggregate in one transaction. Timeout ambiguity keeps
the maximum reservation active until the provider result or
deployment-bounded ambiguity window resolves it; an unresolved expiry records
unknown sources, increments unknown count, and charges the reserved maximum to
the conservative estimated/budget-charge bucket without pretending it was an
actual provider cost. Negative usage and floating-point money are invalid.

Detailed reservation/run evidence follows run retention. Daily aggregates are
retained for the budget horizon in section 9. Doctor reports expired
reservations, missing aggregates, and counters that cannot be measured; a
configured hard ceiling fails closed rather than assuming zero.

Admission evaluates the chosen rule at `pricing_effective_at=reserved_at`,
stores the tuple before provider dispatch, and reserves from its exact
integer formula. Later catalog activation or effective-interval expiry does
not reinterpret an admitted reservation. Reconciliation resolves the retained
immutable config snapshot and verifies its catalog/rule fingerprints before
using reported or estimated usage; a missing/mismatched snapshot leaves the
reservation blocking and raises Doctor rather than charging a current price.

closed route-operation registry generated from the mutation routes in
[admin-agent-studio.md](admin-agent-studio.md), including their exact
input/output schema fingerprint. Admin does not fabricate an
`NpAgentPrincipal` or machine scopes: its route service checks the current
staff session, CSRF, `NpCapability`, and target access before reservation.

ordinary input its `input` member is the exact normalized operation input.

vault-operation commitment
`{kind:"vault-request",vaultOperationId,secretVersionId,requestDigest}`.

the secret bytes and frozen operation facts. The raw secret is passed only to
the write-only vault admission path and is never stored in `request_body`.
First admission reserves the stable vault/secret ids and both rows in one
transaction; replay locates them by the invocation owner tuple and recomputes
the commitment with those same ids, so a changed secret conflicts without
persisting or exposing it. No other ad hoc masking token is canonical input.

`authorization_context_body` is the authoritative source of the context
fingerprint and retains immutable actor/transport/authority facts even after a
staff foreign key is tombstoned. It contains no bearer secret. Every durable
validation, preview, rollback-plan, or MCP-task child copies the exact body
and fingerprint at admission, then uses the embedded authority ref for live
authorization; neither a digest nor a now-null lookup id can reconstruct or
replace it.

A partial unique index on
`(site_id, actor_kind, actor_fingerprint,
authorization_context_fingerprint, operation_kind, operation_id,
idempotency_key)` applies when the key is present. For OAuth it hashes
transport, principal, client, grant id/version, and audience; for a service
credential it hashes transport, site, principal, rotation family id,
family-authority version, current principal-authority version, and audience
(never individual token id or family generation); for runtime/Admin it hashes
the corresponding immutable run/session
authorization context. Raw token material is never included. The same tuple
and request hash returns the recorded accepted/approval/completed/failed
result; a different hash conflicts. Task/resource visibility requires this
same fingerprint, so two credentials owned by one principal are not the same
MCP client context. Result/run links are checked same-site logical
references rather than a circular foreign-key graph; Doctor detects orphans.
Thus a live replacement token from the same unchanged family can poll/cancel a
task started by its predecessor, while an independently issued family cannot.
Presented-token, family, and principal revocation/expiry are still rechecked
before task access. Mutation admission fails closed when this row or its audit start cannot be
committed. Expiry never removes an invocation still needed by an active run,
action, approval, or ChangeSet.

MCP task metadata is excluded from the domain `request_hash` but frozen as a
separate execution-mode precondition in the same reservation. The matrix is
exact: first normal admission followed by task mode, or first task admission
followed by normal mode, returns the ordinary top-level `CONFLICT` without an
operation-specific reason-code extension; task replay with another requested
TTL does the same. Task replay with the same TTL returns the one existing task
and its current status while it remains unexpired.
After task expiry, a task-augmented replay returns MCP
`-32602 Invalid params`, the same non-oracular result as an expired task id,
and never attaches a new task to the retained invocation, falls back to its
domain result, or executes again. Normal→normal keeps ordinary invocation
replay. Thus transport preference cannot alter domain idempotency or create
duplicate work.

Its canonical digest is `authorization_context_fingerprint`. Current
authorization resolves the referenced session/family/grant/run plus
principal/user, site membership, versions, expiry, audience, and effective
scope/exposure/capability/resource visibility; the stored values are comparison
facts, not authority by themselves.

One-time plaintext or short-lived browser attenuator operations are the
explicit exception to result replay. Service-token create/rotate and approval
decision-challenge issuance persist
only the redacted resource id, output hash/verifier metadata, and
`one_time_value_issued=true`; plaintext never enters `output_redacted`.
Repeating the same idempotency tuple/request hash returns the typed
`ONE_TIME_VALUE_ALREADY_ISSUED` conflict with the safe resource id and
recovery operation, not the original value. A lost service-token response
requires rotate/revoke with a new key. A lost approval challenge is
superseded by a new challenge generation/new idempotency key, which
invalidates the prior verifier. A different request under the old key still
conflicts normally.

Preview viewer launch is the third exact one-time-output exception. The first
response emits its short-lived launch-exchange secret only in the no-store
HTML bridge and persists `one_time_value_issued=true` plus verifier metadata.
After the ordinary tuple/request-hash comparison, every same-hash replay
returns `ONE_TIME_VALUE_ALREADY_ISSUED` with the safe preview/launch id and
new-launch recovery operation, regardless of whether exchange is pending,
consumed, expired, or superseded. It never reissues the exchange, re-signs the
JWS, resets a cookie, or mints a new launch under replay.
`CONFLICT/PREVIEW_LAUNCH_EXPIRED` applies only when a viewer path/cookie names
an inactive launch. Precedence is always: different request hash → generic
idempotency conflict; same hash → operation-specific one-time rule; only then
ordinary stored-result replay. The Admin operation registry marks these three
operation families so a fourth implicit exception fails exhaustiveness tests.

task-augmented. Normal accepted invocations have no task row.

run cancellation. A late provider/job completion cannot change the task.

principal, and authorization context. Invalid, expired, foreign, revoked, and

### 6.1 `np_agent_changesets`

Stores ownership, state, immutable plan identity, and aggregate result.

Important columns:

- `id`, `site_id`, optional `agent_id`, `agent_version_id`,
  `agent_config_hash`, `principal_id`, `run_id`, and `invocation_id`; all three
  Agent attribution fields are required for a Runtime creator and absent for
  external/staff creators, while shorter-lived run/invocation ids may later be
  nulled under their fingerprint rules;
- immutable non-PII source actor/operation/idempotency fingerprints;
- `title` and bounded operator-visible `summary`;
- exact state;
- positive `draft_version`, canonical editable-envelope `draft_hash`, and
  positive latest `validation_generation`;
- `base_fingerprint`, `plan_hash`, exact nullable `sealed_plan_body`,
  `risk_summary`, and `policy_refs`;
- optional `scheduled_for`;
- required execution-eligibility `expires_at`; expiration cancels a
  non-executing ChangeSet with the exact `CHANGESET_EXPIRED` reason and revokes
  an unconsumed approval rather than adding an undeclared wire state;
- nullable `rollback_window_seconds`, frozen at successful validation from the
  active policy in the exact safe-integer range `60..7_776_000` (30-day
  default, 90-day maximum), and required exactly with `sealed_plan_body`;
- nullable `rollback_eligible_until`, written only at apply as
  `committed_at + rollback_window_seconds`;
- `created_by_user_id` for a human-created plan; exactly one of
  `principal_id`/`created_by_user_id` identifies the creating actor;
- `created_at`, `updated_at`, `applied_at`, `verified_at`, and
  `rolled_back_at`.

`plan_hash` is null while editable. Creation starts at `draft_version=1`; every
accepted edit compare-and-swaps and increments that value, then recomputes
`draft_hash` over the exact canonical editable envelope. Validation allocates a
new `validation_generation` and must still match both values before it can
write a result. Once validation produces a ready plan, the canonical operation
list and relevant policy/base evidence are sealed into
`sealed_plan_body:{schemaVersion:"np.agent-changeset-plan.v1",
planKind:"changeset",siteId,changeSetId,body}` and `plan_hash`. The exact
stored body, including scopes, human capabilities/predicates, policy hashes,
expiry, snapshots, and rollback duration, is the authoritative rehydration
source; derived summary columns must be byte-consistent with it.
Any edit clears the body, hash, frozen duration, prior validation, and
approvals and produces a new draft identity.

### 6.2 `np_agent_changeset_operations`

One ordered resource mutation:

- `changeset_id` and positive unique `ordinal`;
- `resource_kind` (`document`, `navigation`, `theme_tokens`, `setting`,
  `media_ref`, or a later exact kind);
- canonical `resource_key`; document create stores its server-allocated UUID
  when the draft operation is first accepted, before sealing or document-row
  insertion, and replacement/retry by the same `client_operation_id` reuses
  that key;
- a resource-discriminated `operation`: document `create`, `update`, `publish`,
  `schedule`, or `archive`; navigation/theme-token `replace`; setting
  `replace` or `remove`; media-reference `attach` or `detach`;
- `base_version`/ETag and canonical `before_hash`;
- bounded exact `input`;
- optional access-restricted inline `before_snapshot` needed for compensation,
  capped at 256 KiB per operation and 2 MiB for the whole ChangeSet;
- nullable `snapshot_hash`, required exactly with `before_snapshot` and
  computed using `np.agent-changeset-snapshot.v1`; it is distinct from
  `before_hash`;
- validation status/issues and apply/verify result.

The operation table is immutable after sealing except for framework-owned
execution/result columns.
Before sealing, snapshot fields may both be null. Every operation in a
successfully sealed `ready` plan has the exact presence/absence snapshot body
and non-null `snapshot_hash`; an unavailable snapshot is a blocking validation
issue and no `plan_hash` is created.

#### Validation attempts

`np_agent_changeset_validation_attempts` owns each durable validation
generation:

- `id`, `site_id`, `changeset_id`, positive `generation`, `draft_version`, and
  `draft_hash`;
- `admitting_invocation_id`, byte-equal authorization-context
  body/fingerprint, exact `NpAgentInvocationAuthorityRefV1`, requester
  kind/id, and immutable requester fingerprint;
- state `queued`, `validating`, `ready`, `invalid`, or `failed`, plus bounded
  issue/risk/result digest and safe error code;
- `created_at`, nullable `started_at`/`finished_at`, and bounded `expires_at`.

`(site_id, changeset_id, generation)` is unique. The request transaction
creates the invocation and attempt before enqueue. The worker locks both,
re-resolves current authority from the stored ref, and repeats
`changeset:read` plus visibility for every target before reading draft
contents or writing validation evidence. Authority loss sets the attempt to
`failed` with `AUTHORITY_REVOKED`, leaves the ChangeSet editable, and emits no
plan/approval. A later authorized request creates the next generation.

### 6.4 Rollback plan tables

Rollback is a new immutable forward-compensation plan, not a rewrite of the
original operation rows.

`np_agent_changeset_rollback_plans` contains:

- `id`, `site_id`, `changeset_id`, and positive `generation`;
- `admitting_invocation_id`, exact authorization-context body/fingerprint,
  exact `NpAgentInvocationAuthorityRefV1`, requester kind/id/fingerprint, all
  frozen when rollback preparation is requested;
- exact state `preparing`, `invalid`, `ready`, `approval_pending`, `approved`,
  `executing`, `verified`, `failed`, `conflicted`, or `expired`;
- `compensates_execution_id` and the original ChangeSet `plan_hash`/
  applied-result digest;
- current-state `base_fingerprint`, independent `plan_hash`,
  exact `sealed_plan_body`, `risk_summary`, and frozen `policy_refs`;
- nullable `approval_id`, absent before an approval request and required for
  `approval_pending`, `approved`, `executing`, and every approval-related
  terminal outcome; it must target this rollback plan id/hash;
- `expires_at`, bounded by both the ChangeSet rollback-eligibility window and
  required snapshot availability;
- execution/verification result digests, the exact nullable terminal reason
  inventory from `NpAgentRollbackSummary`, and `created_at`, `approved_at`,
  `started_at`, `finished_at`.

`sealed_plan_body` is the complete
`NpAgentChangeSetPlanCanonicalV1` rollback branch, not a summary assembled
from mutable registries. It carries the exact required scopes/human
capabilities/predicates, policy hashes, original snapshot hashes, expected
current versions, compensation operations, and absolute expiry. Rehydration
must reproduce `plan_hash`; every denormalized rollback column/operation row
must match the body before approval or execution.

`(site_id, changeset_id, generation)` is unique and a partial unique index
permits only one non-terminal generation. A rollback plan never changes the
original ChangeSet plan hash, operations, apply result, or approval. Approval
rejection/revocation or operator cancellation maps to `failed`; approval/plan
expiry maps to `expired`. These terminal outcomes release the partial unique
constraint, and a retry creates the next generation instead of reviving the
row.

`np_agent_changeset_rollback_operations` contains:

- rollback-plan id and positive unique `ordinal`;
- original ChangeSet operation id/ordinal, its inline `before_snapshot`/
  `before_hash`, copied `snapshot_hash`, and canonical resource key;
- expected current applied-after hash/version;
- exact compensation input derived from that original inline snapshot;
- independently validated current schema/access/side-effect metadata;
- apply-after hash, verification result, and safe error code.

These rows are immutable after sealing except for execution/verification
result columns. An elapsed rollback-policy window, missing/malformed snapshot
body, changed current resource, or cross-site/orphan source fails before the
parent state becomes `rolling_back`.

Approvals are single-use and never authorize a different site, target, hash,
capability contract, Agent scope set, required human capability set,
evidence/preview, policy set, or risk. Expiry/revocation and every digest are
checked again inside the execution transaction. Execution recomputes the
current required human-capability set from target/policy and requires it to
match the MAC-bound statement; there is no fictional executing staff actor for
a scheduled worker.

The three canonical body columns are the authoritative integrity
reconstruction source; denormalized columns must be byte-consistent with them.
They preserve immutable requester/target/run/Agent and decision/revocation
facts even when shorter-lived user, invocation, run, or action references are
later nulled. Each body reparses before its hash/MAC is trusted, is
access-restricted and omitted from ordinary list projections, and is retained
for the complete approval dependency closure. Site deletion removes all three
only with the approval row.

When `requires_live_preview=true`, approval creation requires at least five
minutes remaining and sets `expires_at` no later than the bound preview and
all object expiries. Decision, scheduling, and execution lock/recheck the
exact `preview_id`, ready state, plan/contract/manifest digests, artifact
cardinality/part invariants, `object_state=ready`, object existence, and
content digest. Any expiry, missing object, or integrity mismatch revokes an
unconsumed approval as `target_invalidated/PREVIEW_REQUIRED` and requires a
new preview plus approval generation. The retained manifest digest alone is
never sufficient live evidence in v1.

The two reauthentication requirement columns are part of the statement
hash/MAC. Sensitive/destructive approve resolves to
`recent-staff-primary` with a maximum age of 300 seconds; policy/operation may
shorten or raise a reversible approval to that mode, never lower it.
Challenge issue and approve recheck the same session's server-owned primary
reauthentication fact. The decision fingerprint/time are included in its
hash/MAC; reject/protective revoke do not fabricate a reauthentication fact.
For every approved/rejected row, `decision_human_capabilities` is an immutable
decision-body field, not a cache of the user's later authorization. It must
equal the retained decision body and verify both `decision_hash` and
`decision_mac` after a role change or staff-row deletion. Doctor rejects an
unsorted/missing set, body/hash/MAC mismatch, or a terminal decision lacking
the set/body.

`issueApprovalDecisionChallenge()` is the only challenge issuer. It accepts
approval id, intended purpose, `statementHash`, expected approval version, and
a caller-stable idempotency key from a current same-origin Admin session. Under
the approval lock it rechecks current staff capability and target state,
invalidates any older unconsumed challenge, increments both approval version
and challenge generation, and stores only a verifier bound to approval,
purpose, generation, statement, staff user, session fingerprint, and a
five-minute expiry. The plaintext challenge is returned once. Approve/reject
requires `pending`; revoke permits `pending` or approved-but-unconsumed. The
decision transaction consumes the matching live challenge and state/version
by compare-and-swap. A later revoke therefore issues a fresh `revoke`
challenge after an earlier `approve` challenge was consumed.

Approve/reject persist the immutable decision hash/MAC. Revocation never
overwrites that decision: it appends the separate canonical revocation
hash/MAC and moves the row to `revoked`. A human revoke requires the fresh
challenge and `revocation_kind:"human"`. Authority loss, site deletion,
integrity-key emergency retirement, or target invalidation runs under the
locked deterministic reconciliation path without a browser challenge, uses
the listed non-human kind/code plus a deployment-system fingerprint, and MACs
the revocation record. Expiry moves to `expired` and is not mislabeled as a
human revoke. Concurrent approve/reject/revoke/consume operations serialize on
the row; exactly one valid transition wins.

The approval-integrity keyring is deployment-held and separate from the
database, token-hash keyring, OAuth signing keys, vault KEK, and `NP_SECRET`.
Decision and execution recompute canonical bytes and verify both MACs with the
recorded key id in constant time. Missing key material or a changed statement,
decision, state, or binding fails closed and opens a high-severity integrity
incident. Normal rotation retains an old integrity key until every approval
that names it is terminal and past execution/audit verification retention;
early removal is an explicit audited mass invalidation.

Exactly one requester id matches `requester_kind` at creation. After staff
deletion, a staff requester id may be null while the explicit kind and
fingerprint remain; this tombstoned attribution cannot authorize a new
decision. The same rule applies to `decided_by_user_id` and the immutable
decider fingerprint/decision hash.

`(site_id, target_kind, target_id, plan_hash, generation)` is unique, and at
most one `pending` or `approved` generation exists for the same exact target
statement. Decision, expiry/revocation reconciliation, and dependent
ChangeSet/action/run/rollback-plan transition commit atomically. An unchanged
sealed ChangeSet may request the next generation after an unconsumed approval
expires or is revoked; no terminal approval row is reopened.

### 6.6 Preview and artifact rows

`np_agent_changeset_previews` stores one bounded generation attempt for a
sealed plan:

- `id`, `site_id`, `changeset_id`, `plan_hash`, and positive `generation`;
- frozen exact `preview_contract_body` and its
  `preview_contract_fingerprint`;
- `admitting_invocation_id`, byte-equal authorization-context
  body/fingerprint, exact `NpAgentInvocationAuthorityRefV1`, requester
  kind/id, and requester fingerprint;
- state `queued`, `rendering`, `ready`, `failed`, or `expired`;
- exact diff/check/risk summaries, sorted allowed route set, its
  `allowed_routes_digest`, and nullable artifact-manifest `digest`; the latter
  is required after successful all-or-nothing readiness and remains immutable
  through expiry;
- nullable expected artifact count `0..24`, exact `aus1` upload-set digest,
  and reservation timestamp; all three are null before full-set reservation
  and non-null together before the first storage dispatch;
- nullable single-use internal-render bootstrap `jti`, render-attempt id,
  host-allocated render-session id, issued/expiry/consumed timestamps, all
  state-consistent;
- optional run/job correlation plus safe error code;
- `created_at`, nullable `completed_at`, and nullable `expires_at`.

For a successful generation, `expires_at` is exactly the earlier of the
ChangeSet execution-eligibility deadline and `completed_at + 7 days`. `ready`
is readable/approval-eligible only before that instant. A terminal reconciler
CAS-moves elapsed rows to `expired`; request, approval, schedule, and apply
paths enforce the same boundary synchronously.
`completed_at` and `expires_at` are both null in `queued|rendering`, become
non-null together in the atomic `ready` finalization, and remain immutable
thereafter. A generation that fails before readiness has `completed_at` but
no object-validity deadline; its uploads go directly to cleanup.
Every preview/render/artifact persistence read reparses the retained
`NpAgentPreviewContractCanonicalV1` body, reproduces its fingerprint, and
requires child repeated fingerprints to match. Deployment registry upgrades
never reconstruct an old body from a newer implementation.

`np_agent_preview_artifacts` stores authorized artifact metadata:

- `id`, `site_id`, `preview_id`, immutable positive `ordinal` unique per
  preview, and kind `screenshot` or `report`; interactive HTML is rendered live
  behind the Admin launch contract and is never a stored artifact;
- immutable `preview_contract_fingerprint`, byte-equal to the owning preview
  and render session;
- route/viewport/locale metadata from a closed exact contract plus nullable
  `report_part` and `report_total_parts`;
- opaque site-owned storage key, domain-separated `content_digest`, MIME type,
  and byte size;
- frozen storage adapter id, positive contract version, and fingerprint;
- `object_state` exactly `ready`, `delete_pending`, or `absent`;
- nullable `object_expires_at`; null before all-or-nothing readiness, then set
  byte-equal to the owning preview `expires_at` and immutable through
  `ready→delete_pending→absent`,
  `metadata_prune_at`, `delete_attempt`, nullable `delete_receipt_digest`,
  nullable `delete_status` (`deleted` or `already_absent`), nullable
  `delete_error_code`, nullable `deleted_at`, and positive `row_version`;
- `created_at`.

`metadata_prune_at` is initially `created_at + 365 days` and, when the owning
ChangeSet becomes terminal, is raised to at least that ChangeSet's evidence
prune deadline; it is never shortened.
Artifact reads require `object_state=ready`, a live preview, successful storage
metadata preflight, exact size/MIME, and a recomputed byte-equal content
digest. Artifact wire `expiresAt` is exactly `object_expires_at`; no
independent row deadline is inferred. Cleanup locks the row and CAS-moves
`ready→delete_pending`, then calls
the storage adapter with a stable idempotency key derived from
`siteId/previewId/artifactId/contentDigest` plus the frozen storage-adapter
triple; retries reuse that exact key while `delete_attempt` records the bounded
local call count. Confirmed `deleted` or `already_absent` stores a canonical
deletion-receipt digest and moves to `absent`; an unavailable/ambiguous result
keeps `delete_pending`, records only the safe code, increments the bounded
retry attempt, and is retried. No metadata row is pruned until
`object_state=absent`, `metadata_prune_at` passes, and either the upload has an
authoritative terminal no-effect receipt or every ever-present object has a
valid deletion receipt plus final absence check.
The storage registry retains the exact adapter implementation while any
`ready|delete_pending` row names its triple; a missing/mismatched
implementation blocks reads, cleanup, site deletion, and Doctor rather than
letting a newer adapter reinterpret the opaque key.

The atomic reservation assigns ordinals once from the complete server-derived
capture/report set before any upload row or storage call. Upload, manifest,
Admin/MCP serialization, reconciliation, and deletion always order by that
column; no locator, creation timestamp, UUID, or storage-key sort may
reconstruct it later.

`object_state=absent` has two exact meanings distinguished by the retained
upload journal and immutable expiry: a preallocated, never-readable artifact
whose upload set has not been atomically finalized (`object_expires_at=null`),
or a terminally deleted object. A finalized object's non-null expiry is never
cleared. Only a `succeeded` upload in the same live preview generation may
participate in the single `absent→ready` finalization transaction below. Once
its upload is `failed|cancelled`, its preview is terminal, or deletion has
started, the artifact can never become `ready`.

`np_agent_preview_artifact_uploads` is the row-first object-write journal:

| Column                             | Type                 | Rules                                                                                     |
| ---------------------------------- | -------------------- | ----------------------------------------------------------------------------------------- |
| `id`                               | uuid PK              | Generated upload operation id                                                             |
| `site_id`                          | text                 | Same site as preview/artifact                                                             |
| `preview_id`                       | uuid                 | Same-site owner                                                                           |
| `artifact_id`                      | uuid unique          | Exactly one upload operation per preallocated artifact row                                |
| `upload_set_digest`                | text                 | Byte-equal to the preview's frozen `aus1` digest                                          |

The worker first produces the complete bounded screenshot/report byte set in a
worker-private `0700` spool, normalizes it, and computes every content/request
digest without calling remote storage. A crash in this phase leaves no remote
object and the spool is startup/exit-cleaned. Before any storage write, one
transaction locks the rendering preview, freezes the exact count and `aus1`
digest, and inserts the complete `0..24` artifact set with
`object_state=absent` plus every `queued` upload row, deterministic opaque
storage key, frozen adapter triple, `upload_set_digest`, and exact
upload-request digest. Empty/report-only/screenshot-bearing sets follow the
same transaction; no render-attempt row is required for an empty or
report-only branch. No adapter call is legal without the entire reserved set.
The worker claims an upload by `(id,row_version,attempt)` and writes only the
canonical bytes whose precomputed size/content digest match the request; the
opaque storage key is the exact target and the persisted `npau1_` value is the
adapter idempotency identity.

Composite foreign keys bind `(site_id,preview_id)` to the preview and
`(site_id,preview_id,artifact_id)` to its artifact; `artifact_id` and the
stored `npau1_` idempotency key are independently unique. A queued row has
`attempt=0`, `adapter_operation_status=not_dispatched`,
`ever_observed_present=false`, `observed_object_state=unknown`, and null
start/lease/deadline/operation-receipt/finish/verification fields. Claim
atomically sets `running`, attempt one, `started_at`,
`lease_until<=now+90s`, `call_deadline_at<=now+60s`, and operation status
`pending` before the sole storage dispatch; only the lease owner may dispatch.
There is never a second PUT for that row. Later attempts are authoritative
operation inspections only; automatic inspection stops after attempt five,
then bounded operator recovery may continue through 255 without fabricating a
terminal result. `waiting_inspection` retains the immutable call deadline and
has no live lease. `succeeded` requires terminal `committed`, `present`,
`ever_observed_present=true`, valid `auo1`, and `verified_at`. Terminal
`failed|cancelled` requires terminal `not_started|failed_no_effect`, or
terminal `committed` plus a known object observation and cleanup ownership;
the sole exception is a row atomically cancelled while still
`queued/not_dispatched`, which proves no adapter call was admitted. Every
terminal row has `finished_at` and no lease. Whenever ChangeSet evidence
raises the artifact `metadata_prune_at`, the same transaction raises the
upload `prune_at`; the journal cannot disappear while its artifact remains.

After upload, the worker asks the frozen artifact-storage adapter facet to
resolve the operation. `committed` persists the exact `auo1` receipt, after
which the worker reads back the bounded object, recomputes size/content
digest, and verifies MIME metadata before CAS-storing `succeeded`,
`observed_object_state=present`, `ever_observed_present=true`, and
`verified_at`. Terminal `not_started|failed_no_effect` persists its `auo1`
receipt, records `absent`, and fails the preview generation. A timeout, crash,
lost ack, or `pending|unknown` becomes `waiting_inspection`; reconciliation
resolves the same frozen adapter and identity. Elapsed deadlines only make the
row eligible for inspection—they never imply no effect. Exact matching
committed bytes are adopted as `succeeded`. A committed mismatched object
sets `ever_observed_present=true`, fails the generation, and moves its
artifact to `delete_pending`. `pending|unknown` remains blocking
indefinitely; after process/lease loss the host never blind-reuploads lost
screenshot/report bytes.

When and only when the rows exactly match the preview's expected count and
`aus1` set digest and every upload is `succeeded`, one transaction locks the
preview, complete upload/artifact set, and the render attempt/session only
when those nullable identities exist. It rechecks count/digest/order/
report-part/contracts, recomputes the common completion/expiry instant,
CAS-moves every artifact `absent→ready`, assigns every
`object_expires_at` byte-equal to that preview expiry, stores the manifest
digest, and moves the preview `rendering→ready`. The empty/report-only branch
uses the same finalization without inventing a render row. Thus no partial or
under-counted object set is readable. A crash before that transaction leaves
every artifact unreadable with null object expiry and is either finalized by
reconciliation from the succeeded rows or deleted after the generation
fails. A crash after it leaves the complete ready set and immutable expiry.

`np_agent_preview_viewer_launches` stores independent human launch authority:

- `id` (the claim `launchId`), `site_id`, `preview_id`, staff user id,
  staff-session id, exact session fingerprint/key id, and positive generation
  monotonic per `(preview_id, staff_session_id)`;
- admitting Admin invocation id/idempotency key/request hash, frozen signing
  `kid`, exact allowed-routes digest plus immutable
  `site_authorization_body`/`site_authorization_digest`, fixed `iat`/`exp`, and
  redacted isolated-origin launch path;
- launch-exchange verifier/key id, `exchange_expires_at`, nullable
  `exchange_consumed_at`, and `one_time_value_issued=true`; neither plaintext
  exchange nor JWS is stored;
- state `exchange_pending`, `active`, `superseded`, or `expired`, with
  created/activated/superseded/expired timestamps and terminal reason
  `REPLACED|SESSION_REVOKED|PREVIEW_INVALIDATED|SITE_DELETING` required for
  the last two states.

A partial unique index permits one unexpired `exchange_pending|active` row per
preview/staff-session id and the same two states count toward the at-most-20
per-preview cap under the preview lock. Same-session replacement supersedes
only that row; distinct authorized staff sessions coexist. Exchange performs
the only `exchange_pending→active` transition with a one-time verifier CAS.
Every preview request resolves `launchId` and generation and requires the row
to remain active. Preview edit/cancel/expiry or site deletion terminalizes all
child launches; logout/session revocation makes its row unusable immediately
even before cleanup. Production staff cookies are not accepted by the
isolated preview origin; it reloads the persisted session reference
server-side. The retained exact
`NpAgentStaffSiteAuthorizationCanonicalV1` body is the launch-time integrity
source and must always reproduce its digest; current authorization is
independently recomputed on every request and may be narrower, but never
rewrites the historical body/digest.

`np_agent_preview_render_sessions` stores the bounded authority created by the
one-time render bootstrap:

- `id` (the render token's host-allocated `renderSessionId`), `site_id`,
  `preview_id`, generation, plan hash, render-attempt id, allowed-routes
  digest, and preview-contract fingerprint;
- state `active`, `completed`, `failed`, `cancelled`, or `expired`;
- hash-only cookie verifier plus verifier key id, issued/expiry/closed times;
  null close reason only for active/completed, otherwise one exact
  `CAPTURE_FAILED|PREVIEW_INVALIDATED|SITE_DELETING|SESSION_EXPIRED`;
- exact JSON capture plan of at most 20 sorted
  `{ordinal,route,locale,audience:"public",viewportName,width,height,
deviceScaleFactor,captureTicketDigest,captureTicketKeyId}` entries and a
  same-length consumed-ordinal bitset.

One row is unique per `(preview_id, generation, render_attempt_id)`. Bootstrap
creation and preview `jti` consumption commit atomically. Each capture locks
the row and flips exactly one previously-unset ordinal; all-terminal rows deny
capture, and a row becomes `completed` only when every planned ordinal is
consumed. Capture ticket digests are
`ctv1:hmac-sha256:<keyId>:<43-base64url>` over the exact framed input in the
ChangeSet contract; raw tickets never persist. The cookie verifier and ticket
digests/key ids are never returned by Admin/MCP/API projection.

Screenshot MIME is `image/png|image/webp` and size is at most 2 MiB; report
MIME is `application/json` and size is at most 512 KiB. Report metadata uses
the exact bounded JSON contract and never stores HTML with executable remote
authority. Oversized/wrong-MIME output fails the preview generation before a
ready artifact row is exposed.
One preview has at most 20 screenshots, four reports, and 24 total artifact
rows/references; the shared ChangeSet limits enforce the same counts on
generation, persisted reads, Admin/MCP serialization, and Doctor.

`(site_id, changeset_id, plan_hash, generation)` is unique for previews.
Artifact ids are globally unique lowercase UUIDs, storage keys are unique per
storage adapter, and positive ordinals plus the tuple
`(preview_id,kind,route,locale,viewport-name,report-part)` are unique with
normalized null sentinels. Screenshot rows require both report-part fields
null. Report rows require positive contiguous `report_part`, byte-equal
positive `report_total_parts`, and at most four parts. `content_digest` is
deliberately non-unique so identical screenshots/reports may coexist. No
public/storage-signed artifact URL is created. Viewer and renderer JWS values
are derived, short-lived attenuators and are never stored as reusable artifact
bearer values. Access uses the exact header/JWS and live authorization contract in
[changesets-and-approvals.md](changesets-and-approvals.md). Editing/resealing a
ChangeSet expires prior previews for approval use;
retention cleanup removes storage objects through the installed storage
adapter before deleting artifact rows.

Validation, preview, and rollback-prepare workers share one authority rule:
lock the admitting invocation/generation, re-resolve its exact current
authority reference and static scopes/capabilities, then recheck current
visibility for every affected resource before any protected read. A revoked,
expired, narrowed, deleted, deadline-exceeded, or mismatched authority moves
that generation to its exact failed outcome with `AUTHORITY_REVOKED` and
produces no artifact, rollback plan, or approval. Creator identity is never
substituted for the actor that requested the durable generation.

Indexes cover `(site_id, recorded_at)`, `(site_id, kind, recorded_at)`,
undispatched reconciliation, and retention cleanup. Request paths, query
strings, headers, cookies, stack traces, content bodies, and raw IP addresses
are not event payloads. High-volume request activity is aggregated before event
creation.

The four causal columns are all-null or all-non-null and are server-owned.
They are populated from the capability executor's immutable action context in
the same source transaction as an Agent-caused domain mutation; public
payload, plugin hook output, provider output, and callers cannot write them.
Root/run/action must be same-site and depth must equal the referenced run's
stored depth. `causation` is their exact canonical
`NpAgentEventCausationV1` projection and is immutable through event retention.

Shorter-lived foreign rows may later set all four columns null together, but
the retained `causation` body remains the authoritative event-hash and loop-
evidence source; partial clearing or replacing it with only a digest is
forbidden.

A partial unique index on
`(site_id, source_kind, source_component, kind, deduplication_key)` applies
when the key is non-null. Keys use the exact event grammar and are stable
source/outbox ids, not retry randomness. Same tuple plus `event_hash` returns
the existing event; a different hash is a producer contract conflict, opens
an integrity signal, and creates no second row.

Framework changes that require durable agent/security evidence write the event
inside the source transaction. A reconciliation job finds committed events
whose dispatch enqueue was interrupted.

Creation first persists `pending`, then asks the installed shared enforcement
adapter to install the exact TTL restriction. Only a confirmed adapter result
moves it to `active`; an unavailable/process-local adapter in a multi-node
deployment yields `failed` and the capability must not claim containment.
Expiry is enforced first by adapter TTL. `agent:eventReconcile` then claims the
due row, compare-and-swaps its existing source action into the frozen
compensator path, and dispatches
`agent:actionVerify {siteId, actionId}`. It does not mint an invocation or
require a still-live principal. Only an exact restriction-adapter
`removed|already_absent` receipt atomically writes the source action's
compensation result, marks it `compensated`, and moves this row/containment to
`expired`; failure/unknown keeps the uniqueness guard and retries visibly.
Revoke and site deletion use the same confirmed removal boundary. Proxy
enforcement resolves only this site-scoped subject/action contract and never
accepts a model-supplied address or route pattern.

The subject branches are mutually exclusive. Authenticated rows require
`principal_kind`, forbid every bucket field, and use
`subject_key=principal:v1:<principalKind>:<principalId>`. Opaque rows require
purpose, projection version/fingerprint, and key id and use
`subject_key=bucket:v1:<purpose>:<projectionVersion>:<keyId>:<base64url-hmac>`;
they forbid principal kind. The partial active uniqueness key and every
restriction fingerprint include that complete namespaced tuple. Actor-bucket
projection implementations and HMAC keys are retained by their frozen
version/fingerprint/id until the row is terminal and outside retention.

Proxy enforcement derives the current opaque bucket and every distinct
version/fingerprint/key tuple referenced by an active restriction for that
site/purpose, sorted unique and capped at eight, then checks all candidates in
one adapter request. A rotation that would exceed eight active candidates is
rejected until a restriction expires/is removed; it never makes an existing
row unmatchable. Authenticated checks carry exactly one fully namespaced
principal subject.

`row_version` starts at one and increments on every persisted lifecycle,
receipt, error, or revoke transition. Each install/remove call receives the
currently locked value; accepting its result compare-and-swaps that same
value. A stale or duplicate result re-reads the row and either returns its
matching receipt or conflicts—it cannot advance a newer transition.

Action, containment, and restriction repeat one byte-equal
adapter/version/fingerprint triple. Install, proxy check, verify, expiry,
revoke, and site deletion resolve that exact versioned registry entry; a
newer adapter cannot reinterpret an active restriction. Missing/mismatched
entries fail closed, preserve the uniqueness/cleanup guard, and surface a
blocking Doctor issue until the exact cleanup implementation is restored.

and requires adapter id/version/fingerprint,
config version/hash, separate account-subject key/digest, and destination

from the frozen config snapshot, requires it to equal the retained descriptor,
and recomputes the destination HMAC under the
notification row's frozen destination key and account tuple before opening a
credential. The HMAC has no extractable “account portion”; account continuity
is checked against the separately persisted tuple.

existing `active_destination_key_id` and atomically CAS that key id,
recomputed fingerprint, account tuple, and secret/config projection. A
same-descriptor/account result must be byte-equal. A new destination-HMAC key
is used only for a replacement connection or explicit Admin destination rekey;
that is an intentional retarget event, so already queued rows are
`suppressed/DESTINATION_CHANGED` and are never silently re-signed. Any
descriptor, key, fingerprint, account, or config change likewise suppresses
the old row and never retargets its transition/deduplication key. Credential
rotation is therefore secret substitution under identical semantics, not
permission to change recipient/account.

commit. The global `agent:eventReconcile` sweep finds queued/due rows missed
between commit and enqueue and fans out the same site-stamped job. Claim uses
state/attempt compare-and-swap; adapter idempotency uses the notification
deduplication key, so crash/retry cannot duplicate an already confirmed send.

The shared delivery contract is exact:

```ts
export const npAgentNotificationDeliveryLimits = {

  attemptTimeoutSeconds: 10,

} as const;

type NpAgentNotificationDeliveryResult =
  | { state: "confirmed"; providerMessageId: string | null }

  | { state: "ambiguous"; errorCode: string };
```

Adapter metadata declares `idempotency:"enforced"|"none"`.
`retryable_not_sent` uses the next fixed delay while attempts remain.
`ambiguous` may retry with the same deduplication key only for an adapter that
declares and tests enforced downstream idempotency; otherwise it moves to
`failed` with `DELIVERY_AMBIGUOUS` for human review. `permanent_failure` and
exhausted attempts are terminal `failed`; `confirmed` alone becomes `sent`.
Late results compare the expected attempt and cannot rewrite a terminal row.
The contract guarantees no duplicate after confirmed delivery and never
pretends an ambiguous non-idempotent send was unsent.
`provider_message_id` is an opaque non-secret support receipt of at most 256
characters; it is never rendered as a URL or sent back to a model. The
delivery-result digest and frozen idempotency declaration are required before
`sent` so audit/reconciliation does not discard external confirmation.

## 8. Settings, budgets, and quotas

Site-wide Agent Gateway intent is a separate exact `np_settings` key,
`agents.gateway`:

```ts
interface NpAgentGatewaySettingsV1 {
  schemaVersion: "np.agent-gateway-settings.v1";
  stdio: NpAgentGatewayExposureMode;
  mcpHttp: NpAgentGatewayExposureMode;
  agentHttp: NpAgentGatewayExposureMode;

```

An absent key means all three transports are `disabled`. Deployment config
provides the same per-transport hard ceilings; a site setting may only narrow
them. A service token or OAuth grant freezes another non-disabled ceiling no
broader than both. Increasing a deployment or site value never widens an
existing credential/grant, and lowering either takes effect on the next list,
read, or invocation. `approved-execute` preserves the complete bounded
Gateway feature set but still grants no scope and satisfies no capability
approval. Mixed proposal/effect tools resolve the exact input-selected effect
profile, so `propose` can prepare/request approval without admitting the
effecting branch. The setting contains no host, port, relay, token, or secret.

Site-wide runtime intent is a new exact `np_settings` key,
`agents.runtime`. It includes:

- enabled flag;
- sorted allowed provider ids;
- one exact `budgetCeiling: NpAgentBudgetV1`, whose nulls inherit concrete
  deployment ceilings;
- default exact policy-rule/retention values within the framework maxima; and
- emergency pause `{ paused, reasonCode, actorFingerprint, changedAt }`.

Each active `np_agent_versions.budget` may narrow those ceilings. Missing
per-agent limits do not widen the site limit. Admission acquires the same class
of transaction advisory site lock used by site quotas, measures durable rows,
and fails closed when a configured metric cannot be measured.

Agent runtime usage stays separate from the existing exact `site.quotas`
contract during the first release so adding the feature does not silently
change a shipped settings schema. A later live-contract decision may merge the
inventories.

Money is stored as integer USD micros in v1 and every budget/usage wire carries
`costCurrency: "USD"`. Floating-point currency and provider-neutral mixed
units are forbidden. `cost=null`/`unpriced=true` exists only for a late,
ambiguous, or historically imported provider result after admission against a
known maximum price; the maximum reservation remains charged/blocked until
reconciliation. It is never permission to admit another provider call.

Retention cleanup is a site-stamped durable job, batches by stable cursor, and
must not delete an open incident, active ChangeSet, unconsumed approval, running
job reference, or the only required rollback snapshot. Cleanup produces counts
and safe failure evidence, never row payloads.

Preview cleanup first expires viewer launches/render sessions, waits through
token expiry plus the 60-second skew, and reconciles every artifact-upload
journal row. A never-dispatched queued upload becomes `cancelled/absent`;
running or `waiting_inspection` work becomes eligible for authoritative
adapter-operation inspection after its frozen call deadline, but time plus
skew never converts `pending|unknown` into a terminal result. Terminal
`committed` moves the artifact to cleanup ownership and
`delete_pending`; terminal `not_started|failed_no_effect` proves absence.
Cleanup then CAS-deletes every ever-present private storage object through
`delete_pending` with an adapter receipt, verifies final absence, and marks
the artifact metadata `absent`. It retains every terminal upload row for the
same 365-day evidence horizon as its artifact, and prunes render-session and
viewer-launch children only at their respective deadlines after object
convergence. Preview/artifact metadata, upload set/request/operation receipts,
content/manifest/check digests, and safe deletion receipt stay with the
ChangeSet evidence. Viewer JWS signing/verification material may retire after
the last token expiry plus skew; launch-exchange, session-fingerprint,
render-cookie, capture-ticket, and upload-journal digest/adapter dependencies
remain until no retained child row names them. Missing required keys, a
`pending|unknown` operation, or an object-delete backlog is a Doctor issue,
not permission to infer success or drop rows.

MCP task cleanup first reconciles a `working` task from its immutable terminal
invocation/run outcome, then prunes terminal result plus task row exactly at
`created_at + ttl_ms`. It never deletes a task while working, before the
actual TTL, or after its invocation/run parent. A stale working row past its
own expiry is CAS-terminalized `cancelled` with the exact id-less
`{code:-32800,message:"Task lifetime expired"}` result before immediate
prune; an unexpired row with a missing/malformed immutable parent becomes
`failed` with `{code:-32603,message:"Internal error"}`. Contradictory
parent/task terminal outcomes block cleanup and Doctor.

The initial rollback window is 30 days and the deployment-capped maximum is 90
days. Validation seals the exact `rollback_window_seconds` plus its policy
hashes in the initial plan; apply writes
`rollback_eligible_until = committed_at + rollback_window_seconds`. Required
before snapshots and both initial/rollback sealed plan bodies cannot be pruned
before that time or while a rollback is active. After it expires, cleanup sets
the exact `snapshot_expired` rollback-unavailable reason but retains every
exact `NpAgentChangeSetSnapshotCanonicalV1` reconstruction source with its
digest for the full dependency-closed ChangeSet evidence lifetime. Snapshot
rows, their bodies, owning digests, and the last canonical-hash references are
deleted together only when the terminal ChangeSet evidence closure is itself
eligible for pruning. A UI or agent must never offer rollback merely because
the retained body still exists after the policy window.

Shorter-lived source details use the nullable-reference/fingerprint rules
above. Cleanup nulls those references and verifies the retained digest before
deleting the source row. A material normal audit event, action/ChangeSet
result, incident timeline summary, or feedback attribution therefore survives
without retaining raw provider/event/run context. An action that owns an
unrestored quarantine or other active containment cannot be pruned merely
because 365 days passed; it remains until restoration/replacement records an
exact terminal outcome.

## 10. Site and user deletion

`inspectSiteDeletion()` and `deleteSite()` must add every site-owned agent
table to their exact inventory. Because vault, restriction, and preview
adapters have effects outside Postgres, agent-enabled site deletion is a
durable saga followed by the existing final database transaction; it must not
pretend those effects are transactionally atomic.

`np_agent_site_deletion_sagas` is the durable marker:

| Column                  | Type                 | Rules                                                                |
| ----------------------- | -------------------- | -------------------------------------------------------------------- |
| `id`                    | uuid PK              | Generated                                                            |
| `site_id`               | text unique          | One active deletion saga per site                                    |
| `state`                 | text                 | `prepared`, `cleaning`, `ready_to_commit`, `failed`, or `committing` |
| `plan_body`             | jsonb                | Exact immutable `NpAgentSiteDeletionPlanCanonicalV1`                 |
| `plan_hash`             | text                 | Digest of `plan_body`                                                |
| `site_version_digest`   | text                 | Exact `sdsv1` site-row snapshot digest repeated by the plan          |
| `prepared_at`           | timestamptz          | Canonical transaction instant repeated by `plan_body.preparedAt`     |
| `cursor`                | jsonb                | Exact bounded cleanup phase/target cursor                            |
| `requested_by_user_id`  | uuid nullable        | Current staff requester; may become null after final attribution     |
| `requester_fingerprint` | text                 | Immutable non-PII attribution                                        |
| `last_error_code`       | text nullable        | Safe stable blocking reason                                          |
| `lease_until`           | timestamptz nullable | Bounded worker lease                                                 |
| `created_at`            | timestamptz          | Required; may equal but never substitutes for `prepared_at`          |
| `updated_at`            | timestamptz          | Required                                                             |
| `cleanup_completed_at`  | timestamptz nullable | Required in `ready_to_commit`/`committing`                           |

The server-owned site-version source is exact:

```ts
interface NpAgentSiteDeletionSiteVersionBodyV1 {
  schemaVersion: "np.agent-site-deletion-site-version.v1";
  site: {
    id: string;
    name: string;
    hostname: string | null;
    description: string | null;
    settings: NpSiteRuntimeSettings;
    isDefault: boolean;
    createdAt: string;
    updatedAt: string;
  };
}
```

`site_version_digest` is
`sdsv1:sha256:<43-character-unpadded-base64url>` over SHA-256 of
`u32be(len("np-agent-site-deletion-site-version/v1")) ||
utf8("np-agent-site-deletion-site-version/v1") ||
u32be(len(rfc8785(body))) || rfc8785(body)`. The body is built only from the
strictly parsed canonical `np_sites` row while holding the deletion lock; the
default site remains undeletable. `sdsv1` is a closed raw digest kind outside
the 32-purpose registry.

The prepare transaction takes the site deletion advisory lock, freezes the
site-version source, one database transaction timestamp, row/external
inventory, exact `plan_body`, and `plan_hash`; writes `prepared`; pauses Agent
admission; and makes the site unavailable for normal public, member, Admin,
Gateway, and worker reads/writes with the exact `SITE_DELETING` outcome. The
body's `sagaId`, `siteId`, `siteVersionDigest`, and `preparedAt` must be
byte-equal to their columns. No new site-owned row or site-row edit may be
admitted after that commit. Every claim/cursor transition and the final commit
reparse the body, reproduce `plan_hash`, recompute `sdsv1` from the still-
present fenced site row, and reject any mismatch. Once this prepare
transaction commits, deletion is intentionally non-cancellable: a failed saga
must be retried or completed so that external cleanup and the database cannot
diverge.

The frozen row inventory includes every exact site-owned Agent table except
`np_agent_site_deletion_sagas`; the prepare transaction inserts that marker
only after the inventory is computed. `plan_body.sagaId` reserves its identity.
Every transition and final commit separately requires exactly one marker for
the site with that id and byte-equal `plan_body`, `plan_hash`,
`site_version_digest`, and `prepared_at`. The final transaction recomputes only
the same closed non-marker inventory, then deletes the verified marker at step
8 below. A zero-count marker assumption or a second marker is a hard contract
failure.

Every Agent action commit, provider/notification result CAS, connection
operation transition, and worker claim takes the same transaction-scoped site
deletion lock and rechecks the saga before changing ordinary state. After
`prepared`, only a cleanup transition bearing this saga id and `plan_hash` may
write. An in-memory adapter result that arrives later is discarded after safe
metrics/audit correlation and cannot recreate a row, activate a secret, send a
follow-up job, or commit a content mutation.

The cleanup worker is idempotent and records each outcome in the existing
target row before advancing its cursor:

1. cancel/terminalize queued Agent jobs where the queue supports it; atomically
   CAS every working MCP task to `cancelled` with the exact id-less
   `{code:-32800,message:"Site deletion cancelled task"}` result and request
   cancellation of every non-terminal run, action/execution, provider call,
   notification send, and connection operation; broadcast local aborts; then
   wait through their frozen call/attempt deadline plus the shared 60-second
   clock-skew bound before cleanup-fencing any nonresponsive row into its
   exact `cancelled`, `failed`, or `ambiguous` terminal outcome without
   replaying an external call;
2. remove every shared actor restriction and persist its exact adapter removal
   receipt/state;
3. revoke provider OAuth setup requests and destroy their temporary verifier
   leases;
4. revoke connections and destroy/verify every external vault credential,
   first inspecting every non-terminal vault operation and recovering any
   crash-orphaned ref, then persisting `destroyed` secret-version metadata and
   clearing the locator only after the exact adapter result;
5. under each preview lock, invalidate an unconsumed bootstrap `jti`, CAS
   every `exchange_pending|active` viewer launch to `expired` with
   `expired_at`/`SITE_DELETING`, CAS every active render session to
   `cancelled` with `closed_at`/`SITE_DELETING`, and CAS every non-expired
   preview to `expired`; wait until all already-issued viewer/render tokens and
   cookies are past expiry plus 60-second skew;
6. cancel every never-dispatched queued artifact upload. For each claimed or
   dispatched row, wait until its call deadline before authoritative
   operation inspection, then require an exact `auo1` terminal resolution.
   `not_started|failed_no_effect` permits `cancelled/absent`;
   `committed` moves the artifact to `delete_pending` and records
   `ever_observed_present` when read-back finds an object;
   `pending|unknown` blocks the saga indefinitely—neither the 60-second skew
   nor object HEAD is a terminal-operation fence. A succeeded but unfinalized
   upload is adopted only as cleanup evidence and can never make the expired
   preview ready;
7. CAS every `ready` or cleanup-owned `delete_pending` preview/report object
   through the stable deletion protocol, call the frozen storage adapter, and
   persist a confirmed deleted/already-absent receipt plus
   `object_state=absent`. Advance only after the upload operation is
   authoritatively terminal and final absence is verified, so no future write
   can land behind the deletion cursor.

An unavailable, failed, or ambiguous external result leaves the site in the
non-serving deletion state and retries from the persisted target; it never
rolls the database marker back to an apparently healthy site. Doctor/Admin
shows the safe target fingerprint, phase, attempts, and error code. Every
adapter call for a newly saga-owned target uses a stable deletion idempotency
key derived from saga, target, and version. A target row that already owns a
stable external-effect key—especially an artifact in `delete_pending`, vault
operation, connection operation, or restriction removal—must reuse that
existing key and frozen request digest; the saga adopts its receipt/state
rather than changing identity or redispatch semantics.

Only `ready_to_commit` may enter the final serialized database transaction.
That transaction rechecks the plan hash, absence of new rows, and every
external cleanup receipt, then deletes in this order:

1. notifications and feedback;
2. actor restrictions whose external-removal receipts are confirmed, incident
   joins/timeline, incident rows, signals, then normalized events;
3. terminal connection-operation rows; terminal preview-artifact-upload rows,
   absent preview-artifact rows, viewer launches and render sessions, then
   preview rows; containments, actions, ChangeSet executions, rollback
   operations/plans, approvals, original operation snapshots, and ChangeSets;
4. circuit breakers, provider calls, usage reservations/aggregates, terminal
   MCP task rows, then run-step/run rows and their invocation rows; triggers,
   agent versions, policies, and agents;
5. service tokens, OAuth codes, authorization requests, refresh-token
   families, and grants;
6. provider setup-request metadata, cleared connection active-version
   pointers, terminal vault-operation rows, local vault ciphertext rows,
   destroyed secret-version metadata, immutable connection config-version
   rows, and connection metadata;
7. principals and OAuth client registrations that belong only to the site;
8. the deletion saga row, then the remainder of the existing exact site
   deletion graph and `np_sites` row.

A final transaction failure keeps the saga and all already-cleaned target
receipts in `ready_to_commit`/`failed`, with the site still non-serving, so a
retry can finish without recreating credentials or restrictions.

The final transaction refuses a working MCP task; a non-terminal run,
action/execution, provider call, notification send, connection operation,
vault operation, or artifact-upload operation; any attempted upload whose
adapter operation is `pending|unknown` or lacks a valid terminal `auo1`
receipt; any `exchange_pending|active` viewer launch or active render session;
any preview artifact whose object is not `absent`, or whose upload resolved
`committed` or ever observed `present` lacks a validated deletion receipt and
final absence check; a restriction without a confirmed external-removal
receipt; or any
connection-operation reference to an invocation/setup request/secret version
that the plan did not freeze.
Doctor reports these as blocking `agents.contract` deletion-saga issues rather
than silently deleting the parent row.

Before deleting Agent versions, deletion clears `np_agents.active_version_id` and
`draft_version_id` in the same serialized transaction. Implementations may use
deferrable same-site foreign keys, but may not weaken the cross-site checks to
avoid that cycle.

Deleting a staff user does not erase historical action/approval attribution.
Before user-owned references are nulled, deletion revokes active OAuth grants
and service tokens whose authority is that user and suspends their principals
and Runtime Agents. The same serialized authority-change transaction revokes
every unconsumed `pending`/`approved` approval requested or decided by that
user and applies the target-specific dependent transition: an unscheduled
sealed ChangeSet returns to `ready`, a direct action/run becomes `failed`, and
a rollback plan becomes `failed` or `expired` with its exact reason. A
scheduled ChangeSet approval is still unconsumed: authority loss revokes it,
cancels the queued admission, and moves the parent to `apply_failed` with
`APPROVAL_REVOKED` before any domain write. An already consumed approval is
necessarily attached to an applying or terminal execution; it remains
immutable history and cannot authorize future work. A deployment-authority
principal is unaffected merely because its historical creator is deleted.
`created_by`, `owner_user_id`, and decision fields then become null while immutable audit
metadata retains a non-PII actor kind/id hash as allowed by the existing audit
contract.

## 11. Transfer, backup, and migration

- Content transfer excludes every table in this document, the `agents.gateway`
  and `agents.runtime` settings, secrets, policies, signals, incidents, and
  history.
- Physical database/media backup includes them naturally. Restore validation
  checks that vault master-key configuration can decrypt or intentionally
  revoke restored credential rows before enabling Agent Runtime.
- Agent schema changes use normal reviewed Drizzle migrations. Runtime Agents
  cannot create or apply them.
- Doctor adds a single aggregate `agents.contract` check with sub-issues for
  malformed rows, cross-site references, impossible states, orphan jobs,
  undecryptable secret references, stale approvals, MCP task/result/TTL
  divergence, preview launch/render/artifact/part/object-receipt divergence,
  deletion-saga ordering, and retention backlog. The owning MCP and ChangeSet
  documents define the exact subchecks.
- Admin Health reports only counts, adapter readiness, budget posture, and safe
  stable error codes.

## 12. Locked schema choices for the first implementation

The first schema PR must implement these decisions rather than reopen them:

1. Remote interactive MCP ships with the built-in NexPress OAuth 2.1
   Authorization Server. External OIDC is staff-login federation only.
2. Vault mode defaults to `disabled`. Development may explicitly select the
   Postgres-backed `local-envelope` adapter with a dedicated 32-byte master
   key. Production and hosted readiness always reject `local-envelope`; no v1
   escape hatch exists, and a custom KMS/HSM/secret-manager adapter is
   required.
3. Service credentials always expire. The deployment-capped maximum is 90 days
   in production/hosted mode and 365 days in development; rotation may use a
   short, audited overlap.
4. ChangeSet before snapshots are access-restricted inline JSONB envelopes,
   capped at 256 KiB per operation and 2 MiB per ChangeSet. Media operations
   snapshot metadata/references, never binary objects. Oversized plans fail
   validation rather than moving rollback evidence to an implicit storage
   side channel.
5. Incident retention is one site-wide bounded setting in v1. Category-specific
   retention and legal hold are absent until hold scope, authority, expiry,
   deletion precedence, and policy precedence have a separate exact contract.
6. OAuth state lasts 10 minutes, authorization codes 5 minutes, access tokens
   10 minutes, refresh inactivity 7 days, and a refresh family at most 30 days,
   with 60 seconds maximum verification clock skew. Deployment policy may only
   shorten those bounds.
7. Gateway exposure is the ordered `disabled`, `read`, `propose`,
   `approved-execute` inventory at deployment, site, and immutable
   credential/grant layers. Remote MCP uses only the canonical application's
   HTTPS listener and is absent by default; no schema stores an MCP port,
   relay, or tunnel. The maximum explicit mode preserves the complete bounded
   tool/capability inventory without granting scopes or approval.
